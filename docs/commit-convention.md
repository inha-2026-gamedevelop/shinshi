# 신시 커밋 컨벤션

2026-10-01 그믐 저장소의 커밋 규칙(`CONTRIBUTING.md` 2장, 커밋 스킬)을 신시 조건에 맞춰 이식했다. 커밋 메시지 형식은 이 문서가 유일한 기준이다. 브랜치·소유권·비밀값 같은 공통 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

브랜치가 사람 단위(`feature/{팀원이름}`)라 브랜치 이름으로는 무엇을 했는지 알 수 없다. **커밋 메시지가 유일한 이력 단서다.**

## 1. 형식

```
<타입>: <무엇을 했는지>

<왜 했는지 - 필요한 경우만>
```

- 제목과 본문 사이는 빈 줄 하나.
- 제목은 한국어로, 50자 안팎의 한 줄로 쓴다. 끝에 마침표를 찍지 않는다.
- 제목은 결과를 짧게 쓴다. `~추가`, `~수정`, `~변경`, `~제거`처럼 명사형으로 끝내거나 `~한다`로 끝낸다.
- 코드 식별자·파일명·경로는 원래 표기 그대로 쓴다 (`PlayerHealth`, `Dev_Combat.unity`).
- 본문은 제목만으로 이유가 안 드러날 때만 쓴다. 무엇을 바꿨는지 나열하지 말고 **왜** 바꿨는지, 어떤 문제를 해결했는지를 쓴다. 한 줄은 72자 안팎에서 줄바꿈한다.
- 관련 이슈가 있으면 본문 마지막 줄에 `#번호`로 적는다. 이슈를 닫는 연결은 PR 본문에서 한다.

## 2. 타입

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능, 플레이어가 체감하는 동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `docs` | 문서만 |
| `chore` | 설정, 패키지·외부 에셋 도입, 빌드·CI, 밸런스 수치 조정 |

헷갈리는 경우.

| 변경 | 타입 |
|---|---|
| 기능 코드와 그 테스트를 함께 추가 | 기능의 타입 (`feat`/`fix`) 하나로 |
| 기존 버그를 막는 테스트만 추가 | `fix` |
| Asset Store·외부 에셋 도입 (`Assets/99.ThirdParty/`) | `chore` |
| 씬·프리팹에 오브젝트를 배치해 기능을 연결 | `feat` |
| SO·데이터 테이블 수치만 조정 (의도한 밸런스 변경) | `chore` |
| 수치가 기획서와 달라서 바로잡음 | `fix` |
| 재질·조명·지형 같은 아트 설정 조정 | `chore` |
| 기능 구현과 그 기능을 서술한 설계 문서 동기화 | 기능의 타입 하나로 (문서를 따로 떼지 않는다) |

목록에 없는 타입(`style`, `perf`, `test` 등)과 스코프 괄호(`feat(net):`)는 쓰지 않는다. 필요하면 팀이 합의한 뒤 이 표에 먼저 추가한다.

## 3. 예시

```
feat: 패링 판정을 서버 타임스탬프 기준으로 처리

클라이언트 입력 시각을 Command로 함께 전송하도록 변경.
지연 150ms 환경에서 판정이 밀리던 문제 해결.
```

```
fix: 재접속한 파티원의 부적 슬롯이 비어 보이는 문제 수정
```

```
chore: 숲 1웨이브 잡귀 체력을 기획서 초기안으로 조정
```

```
docs: 보스 입장권 차감 시점을 기술설계서에 명시
```

나쁜 예.

| 메시지 | 문제 |
|---|---|
| `수정` / `작업중` / `asdf` | 무엇을 했는지 알 수 없다 |
| `feat: 전투 개선 및 UI 수정 및 버그 수정` | 한 커밋에 여러 일 |
| `Fix: Player bug.` | 타입 대문자, 영어 제목, 마침표 |
| `feat: 코드 추가` | 무엇을 추가했는지 없음 |

## 4. 커밋 단위

- **커밋 하나에 한 가지 일만 담는다.** 관련 없는 변경(문서 정리 + 전투 코드 + 설정)이 섞였으면 나눈다.
- 자연스럽게 하나인 작업은 억지로 쪼개지 않는다. 목적은 이력을 읽기 좋게 만드는 것이다.
- 에셋은 `.meta`와 같은 커밋에 넣는다. 이동·이름 변경은 Unity 에디터에서 한 결과를 커밋한다 ([씬 · 에셋 안전](unity/SCENE_AND_ASSET_SAFETY.md)).
- 서로 다른 씬 파일의 변경은 한 커밋에 섞지 않는다. 씬은 머지가 사실상 불가능해 되돌릴 단위가 작아야 한다.
- 기능의 구현 상태나 팀 계약이 바뀌었으면 그것을 서술한 기준 문서(`docs/`)도 같은 커밋에서 고친다. 문서만 대량으로 손보는 작업은 `docs:` 커밋으로 분리한다.
- 커밋 전에 C# 변경분은 [코딩 컨벤션](coding-convention.md) 위반을 먼저 고친다.
- 비밀값(키, 토큰, 비밀번호)과 개인 기록(`.claude/docs/`, `.claude/handover/`)은 커밋하지 않는다.

## 5. 트레일러와 병합

- AI 도구가 붙이는 `Co-Authored-By` 트레일러는 넣지 않는다. 도구 기본 설정이 붙여도 지운다. 이미 붙었고 push 전이면 `git commit --amend`로 지운다.
- `develop`과 `main`에는 직접 커밋하지 않는다. `feature/{팀원이름}`에서 커밋하고 `develop`으로 PR을 올려 병합한다. `develop`을 `main`에 반영하는 시점은 통합 담당이 정한다.
- GitHub PR 병합이 만드는 `Merge pull request #...` 메시지는 그대로 둔다. 이 형식의 검사 대상이 아니다.
- push한 커밋의 메시지는 고치지 않는다 (강제 push 금지).

## 6. PR 제목

PR 제목도 커밋 제목과 같은 `<타입>: <무엇>` 형식을 쓴다. 여러 커밋을 묶었으면 PR 전체를 대표하는 타입 하나를 고르고, 무슨 기능인지 반드시 제목에 적는다. 본문은 [PR 템플릿](../.github/PULL_REQUEST_TEMPLATE.md)을 따른다.

## 7. 그믐과 다른 점

| 항목 | 그믐 | 신시 |
|---|---|---|
| 기준 문서 | `CONTRIBUTING.md` 2장 | 이 문서. `CONTRIBUTING.md`는 두지 않고 공통 규칙은 `AGENTS.md` |
| 통합 브랜치 | `feature/{이름}` → `develop` → `main` | 같음. 2026-10-01부터 `feature/{팀원이름}` → `develop` → `main` |
| 타입 | 5종 | 같은 5종. 헷갈리는 경우 표와 금지 형식을 추가 |
| 제목 | 형식만 정함 | 한국어·길이·마침표·종결 규칙 추가 |
| PR 제목 | 무슨 기능인지 적는다 | 커밋과 같은 형식으로 통일 |

# 계정·홈페이지 설계

> 기준일: 2026-10-02 · 상태: 설계 / 구현 예정(Codex 교차 검증 2회 반영) · 담당: 민성
> 공개 회원가입, 아이디·비밀번호 로그인, 캐릭터 이름 중복 처리, 가입·로그인 홈페이지의 설계다. 2026-10-02 사용자 결정으로 [기술설계서](../03-technical-design.md) 14장의 "운영자 초대 코드만으로 계정 생성, 회원가입 제외" 규칙을 대체한다. 초대 코드는 운영자 복구 경로로 남는다.

## 1. 결정

| 항목 | 결정 |
|---|---|
| 로그인 수단 | 아이디 + 비밀번호. 런처, 홈페이지가 같은 수단을 쓴다 |
| 이메일 | 가입 때 필수로 받는다. 인증 메일 발송은 나중에 붙이며 그 전까지 `emailVerified = false`로 둔다. 중복은 인증된 이메일 사이에서만 막는다(2장) |
| 가입 대상 | 누구나 가입(공개). 대량 가입은 요청 제한으로 막는다 |
| 닉네임 | 캐릭터 이름이 닉네임이다. 전체 캐릭터에서 중복을 거절한다 |
| 홈페이지 | Vite + React + Tailwind로 만든 정적 사이트가 기존 API를 부른다 |
| 초대 코드 | 운영자가 발급하는 복구 코드로만 남긴다. 플레이어는 홈페이지 복구 화면에서 코드로 로그인한 뒤 아이디, 비밀번호를 정한다(4장) |

## 2. 계정 규칙

| 항목 | 규칙 |
|---|---|
| 아이디 | 4~16자, 영문 소문자, 숫자, `_`. 입력은 소문자로 바꿔 저장하고 비교한다. 중복 거절 |
| 비밀번호 | 8~64자, 영문과 숫자를 모두 포함. 아이디와 같으면 거절. PBKDF2-HMAC-SHA256 600,000회, 16바이트 솔트, 32바이트 결과. 저장 형식 `pbkdf2-sha256$<회수>$<솔트 base64>$<해시 base64>`로 회수를 올릴 수 있게 한다 |
| 이메일 | 254자 이하, 형식 검사, 앞뒤 공백 제거 후 소문자로 만든 `email_key`. 미인증 이메일은 중복을 허용하고 유일 제약은 인증된 행에만 건다(부분 유일 인덱스). 남의 이메일로 먼저 가입해 실제 소유자를 막는 선점을 피하려는 것이다. 인증 기능이 생기면 먼저 인증한 계정이 갖고 같은 키의 다른 미인증 계정은 이메일을 비운다. 그래서 가입 단계에서는 `EmailTaken`을 돌려주지 않는다 |
| 로그인 실패 | 아이디가 없든 비밀번호가 틀리든 같은 거절(`InvalidCredentials`). 없는 아이디도 현재 기본 회수의 PBKDF2를 고정 더미 해시로 계산해 처리 시간을 맞춘다. 기본 회수를 올리면 로그인에 성공한 계정의 해시를 새 회수로 다시 저장해 점차 맞춘다. 타이밍 검증은 벽시계가 아니라 없는 아이디 경로가 PBKDF2를 실제로 호출하는지로 시험한다. 잠금은 계정 전체가 아니라 (아이디, IP) 쌍에만 건다: 같은 쌍 5회 연속 실패 시 그 IP에서만 15분 `AccountLocked`. 다른 IP의 소유자는 막히지 않는다. 같은 공인 IP(NAT)를 쓰는 공격자는 소유자를 15분 단위로 막을 수 있으며, 이는 받아들인 잔여 위험이다. 소유자는 복구 코드 경로로 바로 풀 수 있다(정답 비밀번호로 잠금을 풀어 주면 잠금이 대입 공격을 막지 못하므로 그렇게 하지 않는다). 쌍별 전이: 실패하면 연속 실패 수를 1 올리고 5에 닿으면 잠금 만료 시각을 지금+15분으로 둔다. 잠금 중 요청은 비밀번호를 계산하지 않고 `AccountLocked`로 거절하며 만료를 늘리지 않는다. 만료가 지나면 실패 수를 0으로 되돌린다. 같은 쌍의 동시 요청은 쌍 단위 잠금으로 한 번에 하나씩 전이한다. 아이디 합계 50회는 최근 1시간 미끄럼 창으로 센다. 같은 아이디에 여러 IP 합계 1시간 50회를 넘으면 그 아이디의 비밀번호 시도는 IP마다 1분에 1회로 늦춘다. 성공하면 그 쌍의 실패 수를 0으로 되돌린다. 잠금과 늦춤은 비밀번호 로그인에만 적용하고 갱신 토큰, 초대 코드, 이미 받은 bearer에는 적용하지 않는다. 비밀번호 실패는 bearer 위조 실패 제한기와 섞지 않고 별도 제한기로 센다(같은 NAT의 정상 bearer 사용자를 함께 막지 않게). 카운터는 API 프로세스 메모리에 두며 API를 여러 대로 늘리면 공유 저장소로 옮긴다. 키는 마지막 사용 뒤 1시간 지나면 지우고 전체 10만 개를 넘으면 가장 오래된 것부터 지운다 |
| 요청 제한 | 가입: 형식 검사를 통과한 시도를 IP당 1시간 5회. 아이디 가용성 조회: IP당 1분 30회. 넘으면 `RateLimited`. 비밀번호 해시 계산은 동시 실행을 CPU 코어 수로 제한한다. 대기는 코어 수의 2배까지만 받고 넘으면 바로, 대기 중 2초가 지나면 `RateLimited`로 거절하며, 요청이 취소되면 대기에서 빠진다 |
| 계정 존재 노출 | 아이디 가용성 조회와 가입의 `LoginIdTaken`은 아이디 존재를 알려 준다. 가입 화면 편의를 위해 받아들이고 요청 제한으로 대량 조회를 늦춘다. 로그인 실패는 존재를 구분하지 않는다. `AccountLocked`는 그 IP가 직접 5회 틀린 뒤에만 받으므로 새로 드러나는 정보가 없다 |
| 토큰 | 로그인 성공 응답은 기존 `AuthExchangeResponse`(접근 15분, 회전 갱신 24시간)와 같다 |

비밀번호 원문은 로그, 예외, 응답, DB 어디에도 남기지 않는다. 비교는 고정 시간 비교를 쓴다.

## 3. 캐릭터 이름

| 항목 | 규칙 |
|---|---|
| 처리 순서 | 앞뒤 공백 제거 -> NFKC 정규화 -> 정규화한 값으로 문자, 길이 검사 -> 정규화한 값을 표시 이름 `name`으로 저장 -> `name`을 문화권 독립 소문자(`ToLowerInvariant`)로 바꾼 `name_key` 저장. 조회, 생성, 홈페이지와 게임의 입력 검사가 같은 순서를 쓴다 |
| 길이 | 정규화 뒤 2~12자 |
| 허용 문자 | 정규화 뒤 완성형 한글, 영문, 숫자. 공백과 기호 금지 |
| 중복 기준 | `name_key` 유일 인덱스. 전각, 반각과 대소문자만 다른 이름은 같은 이름이다 |
| 확인 | 입력 중 가용성 조회는 안내용이다. 확정은 생성 요청의 유일 제약이 한다(조회와 생성 사이 경합) |
| 금칙어 | 목록 형식과 관리 주체는 미정 |

## 4. API

기존 v1 규칙(필드 추가만 허용)을 따른다. 경로 상수는 `ApiRoutes`, 거절 코드는 `ContractCodes.RejectReason`과 `ERejectReason`에 함께 둔다.

| 경로 | 인증 | 내용 |
|---|---|---|
| `POST /v1/accounts` | 없음 | 가입. `AccountSignupRequest`(loginId, password, email). 성공 시 `AccountSignupResponse`(accountId, loginId, emailVerified) |
| `GET /v1/accounts/login-id-availability?loginId=` | 없음 | 아이디 사용 가능 여부. 요청 제한 적용 |
| `GET /v1/accounts/me` | 플레이어 | 아이디, 이메일, 인증 여부, 가입 시각 |
| `POST /v1/auth/exchange` | 없음 | 기존 경로에 `loginId`, `password` 필드를 추가한다. 초대 코드, 갱신 토큰, 아이디 비밀번호 중 정확히 하나. 초대 코드 교환은 지금처럼 `build`가 필수다. 아이디, 비밀번호 교환과 갱신 토큰 교환은 `build`를 생략할 수 있고(홈페이지, 런처 로그인·자동 로그인, 2026-10-08 결정), 있으면 지금처럼 검사한다. 기존 필드의 의미는 바꾸지 않으므로 v1 안의 추가 변경이다. 게임 빌드 검사는 게임 세션 발급(`POST /v1/auth/game-session`의 build)과 게임 서버 입장(protocolVersion, contentHash)이 맡으므로 마을 입장권(`/v1/town/join-ticket`)과 복귀 입장권 발급은 게임 세션 토큰만 받는다. 그래서 빌드 검사를 거치지 않은 접근 토큰으로는 게임 서버 입장 토큰을 받을 수 없다. 점검 중이면 빌드 유무와 관계없이 지금처럼 거절한다 |
| `POST /v1/accounts/credentials` | 접근 토큰만(게임 세션 토큰 거절) | 비밀번호를 바꾼다. 일반 변경은 `currentPassword` 재확인이 필수다. `currentPassword` 없이 바꾸는 것은 복구 코드(초대) 교환으로 시작된 로그인 묶음에서 30분 안에만 허용하며, 아이디가 없는 계정은 이때 아이디, 이메일도 정한다. 확정하면 같은 트랜잭션에서 그 계정의 모든 로그인 묶음, 게임 세션과 남은 초대 코드를 폐기한다 |
| `GET /v1/characters/name-availability?name=` | 플레이어 | 캐릭터 이름 사용 가능 여부 |
| `POST /v1/characters` | 플레이어 | 캐릭터 생성(이름 포함). 이름 중복은 `CharacterNameTaken` |

| 거절 코드 | 값 |
|---|---|
| `CharacterNameTaken` | 1001 |
| `InvalidCharacterName` | 1002 |
| `LoginIdTaken` | 1200 |
| `EmailTaken` | 1201 |
| `InvalidLoginId` | 1202 |
| `InvalidEmail` | 1203 |
| `WeakPassword` | 1204 |
| `InvalidCredentials` | 1205 |
| `AccountLocked` | 1206 |

`EmailTaken`은 이메일 인증 기능에서 쓰려고 번호만 잡아 둔다.

## 5. DB

새 마이그레이션(작성 직전 빈 번호 확인)에서 `account_credentials`(account_id PK/FK, login_id 유일, password_hash, email, email_key, email_verified, created_at, updated_at, `email_verified = true`인 행의 email_key 부분 유일 인덱스)를 만들고 `characters`에 `name`, `name_key`(유일) 열을 추가한다. 기존 캐릭터 행이 있으면 이름을 채울 수 없으므로 열 추가 전에 행 수를 확인하고, 있으면 임시 이름 부여 규칙을 정한 뒤 진행한다.

## 6. 홈페이지

| 화면 | 내용 |
|---|---|
| 첫 화면 | 게임 소개 배너, 가입과 로그인 버튼, 런처 내려받기 자리 |
| 회원가입 | 아이디(입력 중 중복 확인), 비밀번호와 확인, 이메일, 약관 동의. 규칙 위반은 칸 옆에 바로 표시 |
| 로그인 | 아이디, 비밀번호. 실패는 한 문구로 안내 |
| 내 정보 | 아이디, 이메일과 인증 여부(인증 메일 미구현 안내), 비밀번호 변경, 캐릭터 이름 중복 확인, 캐릭터 목록 자리 |
| 계정 복구 | 운영자에게 받은 복구 코드로 로그인한 뒤 아이디(없으면), 이메일, 새 비밀번호를 정한다 |

- 위치: `Web/` (저장소 루트). 빌드 결과는 정적 파일이며 로컬에서는 Vite 개발 서버의 프록시로, NAS에서는 역방향 프록시로 같은 출처에서 `/v1`을 API로 넘긴다. 그래서 API에 CORS를 열지 않는다.
- NAS 배치 조건: 역방향 프록시는 한 단만 두고 그 주소를 API의 신뢰 프록시(`KnownProxies`)에 넣는다. 그래야 API가 `X-Forwarded-For`로 방문자 IP를 복원하고, 모든 방문자가 프록시 IP 하나로 묶여 요청 제한을 함께 쓰는 일을 막는다. 배치 후 서로 다른 외부 IP의 요청이 따로 세어지는지 확인한다.
- 웹의 접근 토큰은 메모리에만 두고 갱신 토큰은 웹에 저장하지 않는다. 새로고침하면 다시 로그인한다. 웹 자동 로그인은 범위 밖이다.
- 디자인은 ui-ux-pro-max 스킬로 정하고, 런처와 같은 어두운 바탕과 주황 강조색을 쓴다.

## 7. 런처 영향

런처 로그인 화면은 초대 코드 대신 아이디, 비밀번호를 받고 `AUTH_EXCHANGE`의 새 필드로 로그인한다. 런처는 로그인 요청에 설치 빌드를 싣는다. 복구 코드 입력은 런처에 두지 않고 홈페이지 복구 화면으로 안내한다. 자동 로그인(DPAPI 갱신 토큰), 게임 세션 전달은 그대로다. 런처에 "회원가입" 링크를 두어 홈페이지 가입 화면을 연다.

## 8. 잔여 위험

| 항목 | 내용 |
|---|---|
| 같은 NAT 잠금 | 같은 공인 IP의 공격자는 소유자의 비밀번호 로그인을 15분씩 막을 수 있다. 복구 코드로 풀 수 있다 |
| 기존 bearer 실패 제한 | 위조 bearer 20회/분이 같은 IP의 정상 bearer 요청까지 막는 기존 동작은 이번 범위에서 고치지 않는다 |

## 9. 미정

| 항목 | 담당 | 필요 시점 |
|---|---|---|
| 인증 메일 발송 수단(SMTP, 외부 서비스) | 민성 | 인증 메일 구현 전 |
| 캐릭터 이름 금칙어 목록과 관리 주체 | 민성 | 캐릭터 생성 공개 전 |
| 비밀번호 찾기(이메일 인증 뒤) | 민성 | 인증 메일 구현 뒤 |
| 약관, 개인정보 처리 문구 | 사용자 | 외부 공개 전 |
| 계정당 캐릭터 수 | 기획 | 캐릭터 생성 구현 전 |

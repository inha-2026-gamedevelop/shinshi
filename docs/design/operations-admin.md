# 운영 도구·로그 설계

> 기준일: 2026-10-02 · 상태: P0 API 구현됨(U25)·운영 실행 미검증, P1·P2는 설계 / 예정 · 담당: 민성(API·DB·어드민)
> 운영자 보상·이벤트·공지·제재·장애 복구를 처리하는 어드민 도구와 자체 로그 체계의 설계다. P0 범위는 마이그레이션 `0008_admin_operations`, `/admin/v1` API, 플레이어 우편함 API로 구현했고 백엔드 자동 테스트(실제 PostgreSQL)를 통과했다. 명령줄 도구(`Backend/src/Shinshi.AdminCli`)는 HTTP 대역 테스트와 PowerShell 인자 전달 검증을 수행했고, 실제 API를 향한 조작과 배포 환경의 운영 실행은 검증하지 않았다. 각 절의 "구현(U25)"이 현재 코드이고 나머지 본문은 설계다. 실행 방법·엔드포인트 표·배포 절차는 [Backend README](../../Backend/README.md)의 "운영자 어드민 기반 (0008)" 절, 계약의 기준은 [기술설계서](../03-technical-design.md) 10장, 테이블은 [아키텍처](../04-architecture.md) 7장, 작업 순서는 [구현 로드맵](../05-implementation-roadmap.md)이다.

## 1. 목적과 범위

온라인 게임은 출시 뒤 운영자가 게임 데이터를 바꿀 일이 반드시 생긴다. 장애 보상, 이벤트, 지급 사고 회수, 부정 사용자 제재가 대표적이다. 이 작업을 DB 직접 수정으로 하면 [기술설계서](../03-technical-design.md)의 원자성·중복 방지 계약이 깨지고, 사고가 나도 누가 무엇을 했는지 알 수 없다. 이 문서는 그 작업을 게임과 같은 계약 안에서 처리하는 도구를 정의한다.

| 포함 | 제외 |
|---|---|
| 운영자 지급·회수, 우편, 쿠폰, 기간제 이벤트, 공지·점검, 기능 차단, 계정 조회·수정·제재, 장애 세션 복구, 초대 코드 발급, 경제 원장·감사 로그·지표 | 결제·환불(상점 없음), 채팅 모니터링(채팅 미정), 고객 문의 전용 시스템(외부 폼으로 대체), 유저 경매장 운영(후속 F04) |

## 2. 원칙

1. **어드민도 게임 API를 거친다.** 어드민 도구(체험판은 명령줄 도구, 화면은 P1 이후)는 DB에 직접 접속하지 않고 API의 어드민 경로만 호출한다([기술설계서](../03-technical-design.md) ADR02 "API만 PostgreSQL 쓰기"와 같다). 운영자 지급도 `operationId`를 가진 원자 작업이며 드롭·낙찰과 같은 검증(음수 금지, 공간, 중복)을 받는다.
   웹 화면(`Shinshi.Admin.Web`, 2026-10-07)도 같은 어드민 API만 부른다.
2. **재화·아이템이 바뀌는 모든 경로는 원장에 남는다.** 게임 보상이든 운영자 지급이든 같은 원장에 사유 코드와 출처를 남긴다. 원장에 없는 변화는 버그다.
3. **운영자의 모든 쓰기는 감사 로그에 남는다.** 조회도 개인정보가 보이는 화면은 남긴다. 감사 로그는 추가만 가능하다.
4. **되돌릴 수 있게 만든다.** 일괄 지급은 미리보기 → 승인 → 실행 순서이고, 실행 단위(`grantId`)로 미수령분을 취소할 수 있다.
5. **게임 규칙을 바꾸는 운영 설정은 세션 시작에 고정한다.** 이벤트 배율이 전투 도중 바뀌어 같은 세션 안에서 보상 기준이 달라지지 않게 한다.

## 3. 기능과 단계

### 3.1 운영자 지급과 우편함

- 지급 단위는 `admin_grants` 한 건이다. 대상(계정 목록 또는 조건), 보상 목록, 사유, 수령 기한, 작성자·승인자를 가진다.
- 지급은 대상 계정의 **우편함**에 넣는다. 우편함은 기존 보상 회수함(`reward_inbox`, [기술설계서](../03-technical-design.md) 7.2)을 확장하고 출처 종류(`source_kind`)로 구분한다. 회수함은 원래 획득 +30일, 운영자 우편은 지급별 기한(초기안 30일)이다.
- 멱등 키는 `(grant_id, account_id)`다. 같은 지급을 두 번 실행해도 한 계정에 한 번만 들어간다.
- 캐릭터별 자산(정기·정련편·장비)은 계정 우편으로 보내고 수령할 캐릭터를 수령 시 고른다. 직업 제한 아이템은 맞는 캐릭터만 받을 수 있다.
- **일괄 지급(P1)**: 조건(예: 특정 시각에 접속 중이던 계정, 특정 세션 참가자)으로 대상을 뽑고 미리보기에서 대상 수와 총 발행량을 보여 준다. 발행 총량이 기준(미정)을 넘으면 두 번째 운영자의 승인 뒤에만 실행한다.
- **회수**: 미수령 우편은 지급 단위로 취소한다. 이미 수령한 자산의 회수는 잔액에서 차감하되 음수로 만들지 않는다. 부족분은 회수 불가량으로 기록하고 운영자가 따로 판단한다. 이미 강화·소모한 장비를 역추적해 되돌리지 않는다.

**구현(U25).** 설계와 다른 점을 먼저 적는다.

- `reward_inbox`는 0008에서 운영자 지급용으로 새로 만들었다. 출처는 `AdminGrant`, `RecoveryCompensation` 둘뿐이며 게임 확보품 회수함(원래 획득 +30일) 흐름은 아직 없다.
- 지급 대상은 계정 ID 목록(1~1000)만 받는다. 작성 때 대상 계정이 하나라도 없으면 지급 전체를 `NOT_FOUND`로 거절하고, 실행은 모든 대상의 우편을 **한 트랜잭션**에 넣는다. 9장의 "일부 실패 시 성공분만 확정·재실행으로 나머지 완료" 대신 전부 아니면 전무로 정했다. 나눠 커밋하면 일부만 들어간 Executed 상태가 생기기 때문이다.
- 상태는 Draft → Executed → Cancelled, Draft → Cancelled다. 승인 단계(`approve`)는 없고 P0에는 2인 승인이 없으므로 실행 감사 행을 `self_approved=true`로 남긴다. 그 대신 대상이 2명 이상인 지급(일괄 지급)과 `RecoveryCompensation` 지급의 실행은 Admin 이상만 할 수 있다. Operator가 부르면 403 `FORBIDDEN_ROLE`이다.
- `RecoveryCompensation`은 복구 대상(세션 ID, `sourceRef`)당 취소되지 않은 지급 하나만 둔다(0008의 부분 유일 인덱스 `ux_admin_grants_recovery_ref`). 중복 작성은 409 `INVALID_STATE`이며 앞 지급을 취소하면 다시 작성할 수 있다.
- 캐릭터별 자산은 정기(`Essence`)·정련편(`Shards`)만이며 수령 때 캐릭터를 고른다. 장비 인스턴스와 직업 제한 아이템은 지급 대상이 아니다. 아이템은 정산과 같은 허용 ID·`Account` 귀속의 `AccountItem`만 받는다. 행동력은 제외한다.
- 수령 기한은 지급별 `claimDays`(1~365, 기본 30)다. 한 줄 수량 상한 1,000,000은 오타 방지용 임시값이다.
- 회수는 개인 조정(`POST /admin/v1/accounts/{id}/adjustments`, 음수 delta)이다. 잔액에서 예약분(출정 티켓, 경매 입찰금, 지참 물약)을 뺀 가용량까지만 빼고 모자란 양을 `shortfall`로 응답과 감사에 남긴다. 지급 취소는 기한 안의 미수령 우편만 취소하고 수령분은 건드리지 않는다.
- 플레이어 수령(`POST /v1/inbox/claim`)은 actor가 계정인 원자 작업이고 원장 사유는 출처와 무관하게 `InboxClaim`이다. 목록은 곧 만료되는 순서로 최대 100개다. 계정별 1분에 수령 30회, 목록 60회 한도(429 `RATE_LIMITED`)와 수령 본문 4 KiB 상한(413)을 본문을 읽기 전에 적용하고, 없는 우편과 남의 우편은 작업 행 없이 `INBOX_NOT_FOUND`다.
- 저장된 보상은 읽을 때 구조만 검증한다. 허용 ID·수량 상한은 작성 때만 적용한다. 구조가 손상된 우편은 목록에서 빠지지만 수령과 어드민 조회는 500이다.

### 3.2 이벤트

- `live_events`는 종류, 시작·종료 시각(UTC), 대상(모드·맵·직업), 값을 가진다. 초기 종류는 드롭 확률 배율, 추가 정기 배율, 접속 보상이다.
- 게임 서버는 **세션 시작 때** 활성 이벤트 목록을 받아 세션에 고정하고 `session_events`에 기록한다. 세션 도중 이벤트가 끝나도 그 세션은 시작 기준을 유지한다.
- 배율은 기획 기본값([게임 기획서](../02-game-design.md)와 부록 수치)에 곱한다. 드롭 배율 상한은 3배(초기안)이며 보스 입장권·희귀 재료처럼 경제 영향이 큰 항목은 별도 승인 대상이다.
- 이벤트 설정 변경은 코드 배포 없이 적용한다. 시작 전 이벤트는 수정할 수 있고, 시작한 이벤트는 종료 시각 앞당기기만 허용한다.

### 3.3 공지·점검·기능 차단

| 설정 | 동작 | 읽는 쪽 |
|---|---|---|
| 공지 | 제목·본문·노출 기간·대상(런처/게임/둘 다)·중요도 | 런처 시작 화면, 게임 마을 |
| 점검 모드 | 켜면 신규 로그인·출정 거절 → 진행 세션은 끝까지 진행 → 모든 세션 종료 뒤 서버 교체. 운영자 계정은 예외 | API, 런처, 마을 서버 |
| 기능 차단 | `auction`, `crafting`, `enhance`, `inherit`, `gathering`, `boss_entry` 등 기능별 on/off. 꺼진 기능 요청은 `FeatureDisabled`로 거절 | API, 게임 서버 |
| 버전 차단 | 허용 `buildId` 목록에서 제거하면 해당 빌드의 로그인·접속 거절 | API, 런처([런처·패치](launcher-and-patch.md)) |

기능 차단은 경제 사고의 1차 대응이다. 예를 들어 경매에서 중복 지급이 의심되면 서버 전체를 내리지 않고 경매만 끈 뒤 원장으로 범위를 확인한다. 차단 중 진행되던 경매는 [기술설계서](../03-technical-design.md) 9장의 복구 절차로 마감한다.

**구현(U25).** 네 설정 모두 `service_state`(단일 행, revision 낙관적 갱신)와 `service_notices`에 두고 `PUT /admin/v1/service-state`(Admin), `POST /admin/v1/notices`(Operator)로 바꾼다. API는 5초 캐시로 읽고 쓴 인스턴스는 바로 반영한다. 시작 때 백그라운드로 한 번 읽어 두고, 첫 읽기 전의 로그인·공개 상태 조회는 그 읽기를 기다리며 끝내 읽지 못하면 점검 중으로 본다. 0008의 초기 행은 점검 중·허용 빌드 없음이다. 설계와 다른 점은 아래와 같다.

- 점검은 게임 로그인·토큰 갱신과 새 출정 예약을 거절한다. 어드민 계정은 게임 계정과 분리돼 점검의 영향을 받지 않지만, 점검 중에 게임에 들어가는 운영자 게임 계정 예외는 없다. 진행 중 출정의 입장 토큰 교환은 DB 점검을 보지 않고 설정 `ServiceState:Maintenance`를 읽는다(진행 세션 유지를 위해 의도적으로 남김).
- 기능 키는 `auction`, `crafting`, `enhance`, `inherit`, `gathering`, `boss_entry`, `inbox_claim`, `dungeon_entry`이며 목록 밖 키는 저장을 거절한다. 거절 코드는 `FEATURE_DISABLED(1100)`, HTTP 409다. `talisman`, `training`도 같은 목록에 있다. 지금 `ServiceFeatureGate`로 막는 곳은 새 출정 예약(`dungeon_entry`, 보스전은 `boss_entry`도), 우편 수령(`inbox_claim`), 경매 입찰(`auction`, 경매 열기는 막지 않는다), 마을 서버가 중계하는 성장 API(장비 제작 `crafting`·강화 `enhance`·계승 `inherit`, 부적 등록·강화·조합·분해 `talisman`, 수련·재분배 `training`), 생활 API(채집 `gathering`, 물약 제작 `crafting`)다. 장비 착용·해제·잠금·분해와 성장·생활 조회는 기능 키 없이 열려 있다. 게이트 거절은 저장하지 않는다. 막는 동안 같은 operationId 재전송은 저장된 처음 결과를 받고, 차단 중 처음 보낸 operationId는 해제 뒤 다시 오면 실행된다.
- 점검은 우편 수령을 막지 않는다. 점검 중 수령을 허용할지는 정하지 않았다(8장).
- 공지 작성의 형식 검사(길이·대상·시작 < 끝)는 작업 행 없이 400이고, 끝 시각이 지금 이하인지는 멱등 실행 안에서 DB 시각으로 판정해 409 `INVALID_REQUEST`로 저장한다. 확정된 공지를 만료 뒤 같은 operationId로 재전송해도 처음 결과를 받는다.
- 공지는 공개 `GET /v1/service-state` 응답의 `notices` 배열로 내보낸다(노출 중인 것만, 최대 20개). 기존 `notice` 문자열은 노출 중인 런처 대상 첫 공지의 제목이다. 런처·마을 화면의 표시 연결은 이 작업 범위가 아니다.

### 3.4 계정·제재·장애 복구

- 계정 조회는 내부 ID·초대 코드·캐릭터 이름으로 찾는다. 화면에는 개인정보 대신 내부 ID를 보이고, 연락처 같은 식별 정보가 생기면 권한이 있는 역할만 가린 값을 풀어 본다.
- 계정 데이터 수정은 원장에 남는 원자 작업으로만 한다(예: 재화 ±, 해금 부여). 임의 필드 편집 화면은 만들지 않는다.
- 제재(P1)는 기간·사유·근거 로그 링크를 가진다. 정지 계정은 로그인과 신규 출정을 거절하고, 진행 중인 세션은 강제 종료 여부를 운영자가 고른다.
- 장애 복구 화면은 `RecoveryPending` 세션·경매를 보여 주고, 저장된 종료 이벤트로 정산 재시도, 확인된 서비스 장애 취소, 수동 보정 지급을 실행한다. 보정 지급도 3.1의 지급 경로를 쓴다.

**구현(U25).**

- 계정 검색은 계정 ID·캐릭터 ID·초대 코드 원문(HMAC으로 바꿔 검색)이다. 요청 로그에 조회 문자열이 남으므로 초대 원문은 `POST /admin/v1/accounts/search` 본문으로만 받고, `GET /admin/v1/accounts?query=`는 UUID만 받는다. 캐릭터 이름 검색은 없다(이름 열은 0010에서 생겼으나 어드민 검색에 연결하지 않음). 상세 조회는 `reason`이 필수이고 데이터를 읽기 전에 감사 행을 먼저 커밋한다.
- 강제 종료(kick)는 계정의 로그인 묶음과 하위 토큰(접근·갱신·게임 하위 세션·미소비 입장 토큰), `revokeInvites`(기본 true)면 초대도 폐기한다. **현재 접속은 유지한다**(응답 `currentSessionKept=true`). 게임 서버가 쥔 계정 접속 임대는 heartbeat로 계속 연장되고, 폐기된 토큰의 갱신·재접속·새 입장 토큰 발급부터 거절된다. **비밀번호 로그인은 막지 않는다.** 0010의 아이디·비밀번호 로그인이 있으므로 kick 뒤에도 같은 아이디와 비밀번호로 새 토큰을 받을 수 있다. 로그인 차단과 즉시 차단은 제재(P1)와 함께 정한다.
- 복구 대상 목록(`GET /admin/v1/sessions`)은 세션만 보인다. 경매 복구 목록은 없다. 수동 복구(`POST /admin/v1/sessions/{id}/recovery`, Admin)는 `RetrySettlement`(Settling 정산 재시도), `ServiceCancel`(배정 서버 소실이 확인된 Running 장애 취소), `ForceClose`(정산이 5회 이상 실패해 격리된 Settling을 장애 취소와 같은 보상으로 닫음)다. 설계의 "수동 확정"은 `ForceClose`로 대신한다. 원래 정산안이 아니라 장애 취소 보상이므로 차이는 보정 지급으로 메운다. RecoveryPending 상태의 세션은 처리 경로가 없어 `INVALID_STATE`다.
- `RetrySettlement`·`ServiceCancel`은 설계의 "한 원자 작업"과 달리 **두 트랜잭션**이다. 의도 감사 행(`admin.session.recovery.intent`)을 먼저 커밋하고, 정산·장애 취소는 자동 복구와 같은 서버 actor·operationId로 기존 경로가 자기 트랜잭션에서 확정한 뒤, 어드민 작업과 감사 행을 따로 확정한다. 마지막 단계가 실패해도 의도 행이 남는다. `alreadyApplied`는 복구 작업이 이번 호출 전에 이미 저장돼 있었는지다. 서버 복구가 어드민 operations 행보다 먼저 확정되므로, 세 action 모두 시작할 때 운영자 작업 키(운영자, operationId)를 action·대상 세션·요청 해시에 묶는 `admin_operation_claims` 행을 먼저 커밋하고 다르면 복구 없이 `IDEMPOTENCY_CONFLICT`다. 일반 업무 변경도 operations 행을 만들기 전에 같은 추가 전용 결속을 커밋한다. 다른 해시는 operations 행과 효과 없이 거절하므로, 일반 쓰기와 수동 복구가 경합해도 최초 요청만 실행되고 복구의 결과 키를 다른 요청이 점유하지 않는다. 같은 키의 수동 복구 실행은 끝까지 직렬화한다(같은 operationId로 서로 다른 세션을 동시에 복구하거나 어드민 단계 실패 뒤 다른 세션을 복구하는 것을 막음). `ForceClose`는 운영자 작업 한 트랜잭션에서 종결·원장(actor `Admin`)·감사를 함께 쓴다.
- API 시작이나 DB 단절 뒤 30초 동안은 서버 소실 판정을 보류한다(`RecoveryLivenessGate`, 자동 복구와 공유, 프로세스별). 보류 중 새 `ServiceCancel`·`ForceClose`는 503 `BACKEND_UNAVAILABLE`과 `Retry-After`이고, 목록은 `livenessDeferred=true`, `instanceLost=false`로 보인다. 세부는 [Backend README](../../Backend/README.md)의 "장애 세션 복구".

## 4. 로그 체계

로그는 목적에 따라 저장 방식과 신뢰 수준이 다르다. **원장과 감사 로그는 게임 데이터와 같은 DB 트랜잭션**에 쓰고, 나머지는 구조화 로그로 흘린다.

| 종류 | 담는 것 | 저장 | 보존(초기안) |
|---|---|---|---|
| 경제 원장 | 재화·수량형 아이템의 모든 증감 | PostgreSQL, 상태 변경과 같은 트랜잭션 | 영구 |
| 아이템 이력 | 장비 인스턴스의 생성·강화·계승·이동·소멸 | PostgreSQL, 같은 트랜잭션 | 영구 |
| 운영자 감사 | 운영자의 모든 쓰기와 민감 조회 | PostgreSQL 추가 전용 | 영구 |
| 세션 이벤트 | 입장·웨이브·사망·부활·처치·정산 | 기존 `session_events` | 체험판 기간 삭제 안 함 |
| 행동 로그 | 로그인·로그아웃, 성장 시도와 결과, 입찰, 채집 | 구조화 JSON → 로그 저장소 | 90일 |
| 기술 로그 | 오류, 재시도, 지연, 서버 틱, 버전 거절 | 구조화 JSON → 로그 저장소 | 30일 |

로그 공통 키는 [기술설계서](../03-technical-design.md) 10장의 `buildId, contentVersion, instanceId, sessionId, participantId, operationId, eventId, reasonCode`에 `accountId, actorKind`를 더한다. 토큰·비밀번호·초대 코드 원문은 어떤 로그에도 남기지 않는다.

### 4.1 경제 원장

한 행이 자산 한 종류의 한 번 증감이다.

| 필드 | 뜻 |
|---|---|
| `ledger_id`, `occurred_at` | 유일 ID, DB 시각(UTC) |
| `account_id`, `character_id` | 소유자. 계정 공유 자산이면 `character_id`는 비움 |
| `asset_kind`, `asset_id` | 재화 종류(엽전·티켓·정기·정련편·행동력) 또는 아이템 정의 ID |
| `delta`, `balance_after` | 증감량, 변경 뒤 잔액. 예약·해제도 별도 행으로 남긴다 |
| `reason` | `EEconomyReason` 값 |
| `source_type`, `source_id` | 원인 개체(세션·경매·레시피·지급·쿠폰 등)와 그 ID |
| `operation_id`, `actor_kind`, `actor_id` | 원자 작업 ID, 행위자 종류(`Player`/`Server`/`Admin`/`System`)와 ID |

`EEconomyReason` 초기 값은 `SessionReward`, `SessionSettlement`, `BossReward`, `AuctionReserve`, `AuctionRelease`, `AuctionSettle`, `AuctionPayout`, `Training`, `Craft`, `Enhance`, `Inherit`, `TalismanRegister`, `TalismanUpgrade`, `Dismantle`, `Gathering`, `PotionUse`, `PotionReturn`, `TicketConsume`, `TicketRefund`, `InboxClaim`, `InitialGrant`, `AdminGrant`, `AdminRevoke`, `EventReward`, `Coupon`, `RecoveryCompensation`이다. enum 규칙은 [코딩 컨벤션](../coding-convention.md)을 따르고 값은 명시하며 재배열하지 않는다.

불변식: 계정·자산별 `delta` 합계는 현재 잔액과 같다. 매일 한 번 대사(reconciliation) 작업이 이를 검사하고 어긋나면 ERROR 알림을 보낸다.

구현(U25): 운영자 개인 조정은 증가 `AdminGrant`, 감소 `AdminRevoke`(actor_kind `Admin`, actor_id 운영자 ID)로, 플레이어 우편 수령은 `InboxClaim`(actor_kind `Player`, source_type `inbox`, source_id 우편 ID)으로 남긴다. 장애 보정 지급도 우편으로 받으므로 `InboxClaim`이며 `RecoveryCompensation` 사유는 아직 쓰는 경로가 없다. 보정 여부는 우편 행의 `source_kind`로 가린다.

### 4.2 아이템 이력

장비처럼 인스턴스가 있는 아이템은 `item_history`에 `item_id`, 사건(`Created`/`Enhanced`/`EnhanceFailed`/`Inherited`/`Consumed`/`Equipped`/`Moved`/`Deleted`/`Revoked`), 변경 전후 단계·소유자, `operation_id`를 남긴다. 어드민에서 아이템 ID 하나로 생성부터 소멸까지 따라갈 수 있어야 한다.

### 4.3 운영자 감사 로그

`admin_audit_log`는 `audit_id`, 시각, 운영자 ID·역할, 행동, 대상 종류·ID, 변경 전후 값, 사유, 승인 ID, 요청 출처(IP는 해시)를 가진다. API의 DB 계정에는 이 테이블의 UPDATE·DELETE 권한을 주지 않는다. 사유 없는 쓰기 요청은 API가 거절한다.

구현(U25): 0008이 위 열에 `actor_kind`(`Admin`/`System`), `operation_id`, `self_approved`를 더해 만들었다. 런타임 권한은 SELECT·INSERT만이고 0003의 추가 전용 트리거가 UPDATE·DELETE·TRUNCATE를 거절한다. 업무 변경 쓰기(인증 경로인 로그인·로그아웃 제외)는 모두 `operationId`와 `reason`(최대 500자)이 필수이며 효과와 **같은 트랜잭션**에서 감사 행을 쓴다. 업무 거절은 효과와 함께 감사 행도 롤백하므로 감사 로그에는 커밋된 변경만 남고, 거절 시도는 `operations`의 Rejected 결과로만 남는다. 로그인 성공, 로그아웃, 잠금, 계정 상세 조회, 네 로그 조회(원장·아이템 이력·세션 이벤트·작업, 4.4), 세션 복구 의도(`admin.session.recovery.intent`)는 operation 없이 단독 행으로 남긴다(로그인 실패 자체는 남기지 않음). 장애 복구 감사는 3.4의 순서를 따른다. `approval_id`는 2인 승인이 없어 비어 있고 지급 실행만 `self_approved=true`다. 최초 Owner 생성은 actor `System`이다. 요청 IP는 HMAC 해시로 저장하고 조회 응답에는 앞부분만 보인다.

### 4.4 조회 화면

| 화면 | 입력 | 보여 줄 것 |
|---|---|---|
| 계정 재화 흐름 | 계정 ID, 기간, 자산 | 원장 시간순, 사유별 합계 |
| 아이템 추적 | 아이템 ID | 생성부터 현재까지의 이력 |
| 세션 재생 | 세션 ID | 세션 이벤트 전체, 참가자, 정산안과 적용 결과 |
| 작업 조회 | `operationId` | 요청·결과·영수증·관련 원장 행 |
| 운영자 이력 | 운영자 ID 또는 대상 | 감사 로그 |

구현(U25): 화면 대신 읽기 전용 API(Viewer)로 제공한다. 차례로 `GET /admin/v1/ledger`(accountId 또는 sourceType+sourceId 필수, 원장 사유 필터 `reasonCode`, keyset 커서, 필터 전체의 사유·자산별 합계는 첫 페이지에만), `/items/{itemId}/history`, `/sessions/{sessionId}/events`(요약·참가자·이벤트·관련 원장과 작업), `/operations/{actorId}/{operationId}`(작업 행과 같은 작업 키의 원장·아이템 이력·outbox·감사), `/audit`(운영자·대상·기간)이다. 감사 로그를 뺀 네 조회는 계정 데이터가 실리는 민감 조회라 `reason` 조회 문자열이 필수이고, 읽기 전에 감사 행(`admin.ledger.view` 등)을 먼저 커밋한다. 감사 행은 요청(페이지)마다 하나씩 쌓인다. 감사 로그 조회는 감사하지 않는다.

## 5. 지표와 알림

| 지표 | 목적 |
|---|---|
| 동시 접속, 마을·던전 인스턴스 수와 상태, 대기열 | 용량 판단([기술설계서](../03-technical-design.md) 3장) |
| API p50/p95/p99, 오류율, 저장 큐 길이 | 장애 조기 감지 |
| 자산별 일일 발행량(source)·소각량(sink)·순증 | 경제 인플레이션 확인. 설계값은 [성장·경제](growth-economy.md) |
| 강화·등록 성공률 실측과 설계값 차이 | 확률 구현 오류 발견 |
| 세션 결과 분포, 평균 소요 시간 | 5~6분·10~15분 목표 확인 |

이상 탐지 알림 초기안: 계정 하나가 1시간에 자산을 일일 평균 발행량의 10배 이상 얻음, 같은 `source_id`에서 같은 계정으로 중복 지급, 원장 대사 불일치, 음수 잔액 제약 위반 시도, 운영자 지급 총량이 승인 기준을 넘음. 기준값은 체험판 데이터로 조정한다.

## 6. 권한과 보안

| 역할 | 할 수 있는 일 |
|---|---|
| `Viewer` | 조회(개인정보 가림), 로그 검색 |
| `Operator` | Viewer + 개인 지급·회수, 공지, 강제 종료, 초대 코드 |
| `Admin` | Operator + 일괄 지급 실행·승인, 이벤트, 점검·기능 차단, 제재, 장애 복구 |
| `Owner` | Admin + 운영자 계정·역할 관리 |

- 어드민 계정은 게임 계정과 완전히 분리하고 2단계 인증을 필수로 한다. 게임 로그인 토큰으로 어드민 경로를 호출할 수 없다.
- 어드민 경로는 허용 IP 또는 사설망에서만 연다(방식 미정). 운영 비밀값 공급은 [기술설계서](../03-technical-design.md) 15장의 결정을 따른다.
- 일괄 지급 승인자는 작성자와 달라야 한다. 3인 팀이라 P1 전까지는 단독 실행을 허용하되 감사 로그에 표시한다.
- 개발 빌드의 재화 지급 명령([기술설계서](../03-technical-design.md) 13장)은 외부 체험판에서 제거한다. 운영 지급은 이 어드민 경로만 쓴다.

**구현(U25).**

- 역할은 요청마다 인증 미들웨어가 다시 읽고, 쓰기는 효과와 같은 트랜잭션에서 한 번 더 확인한다. 인증 뒤 그 운영자가 비활성화되거나 역할이 인증 때보다 낮아졌으면 진행 중이던 쓰기(운영자 생성 포함)는 확정되지 않고 `FORBIDDEN_ROLE` 거절로 저장된다. 행위자 행을 `FOR SHARE`로 잠가 확인하므로 확인 뒤의 비활성화는 그 쓰기가 끝날 때까지 기다린다. 운영자 비활성화 요청은 행위자와 대상을 ID 순서로 함께 잠가 다시 확인하며, 이미 비활성화된 행위자는 기존 계약대로 `INVALID_STATE`, 역할 하향은 `FORBIDDEN_ROLE`로 저장한다.
- 역할은 `Viewer(0) < Operator(1) < Admin(2) < Owner(3)`이고 높은 역할이 낮은 역할의 권한을 모두 가진다. 실제 배정은 Viewer: 모든 조회·로그·복구 대상 목록, Operator: 지급 작성·취소, 대상 1명인 일반 지급 실행, 개인 조정·공지·강제 종료·초대 발급/폐기, Admin: 대상 2명 이상 지급과 보정 지급(`RecoveryCompensation`)의 실행, 서비스 상태(점검·기능 차단·허용 빌드) 저장, 장애 세션 복구, Owner: 운영자 생성·비활성화다. 지급 상세 조회도 Operator 이상이다. 조건부 일괄 지급·이벤트·제재는 없다. Owner 비활성화는 자기 자신, 그사이 비활성화된 행위자, 마지막 활성 Owner를 거절한다. Viewer의 "개인정보 가림"은 개인정보 열이 아직 없어 따로 처리하지 않는다.
- 운영자 계정은 `admin_users`로 게임 계정과 분리한다. 비밀번호는 PBKDF2-SHA256(600000회), 2단계 인증은 TOTP(RFC 6238, SHA1, 30초, 6자리, 앞뒤 한 스텝, 재사용 거절)이며 TOTP 비밀은 AES-GCM으로 암호화해 둔다. 로그인 실패는 원인과 무관하게 401 `INVALID_CREDENTIALS(9001)` 하나이고 연속 5회 실패면 15분 잠근다. 어드민 토큰은 30분이다.
- 게임 접근 토큰·서버 임대 토큰으로 어드민 경로를 부르면 401, 역할 부족은 403 `FORBIDDEN_ROLE(9002)`, 어드민 토큰으로 플레이어 경로를 부르면 401이다.
- 접근 제한은 설정 `Admin:AllowedNetworks`(CIDR·단일 IP 목록)이며 비어 있으면 루프백만 연다. 허용 밖 요청은 404로 경로의 존재를 숨긴다. 판정은 forwarded headers 처리 뒤의 원격 주소다. 신뢰 프록시(`ForwardedHeaders:KnownProxies`)가 허용 범위 안에 있으면 시작을 실패시키고, 신뢰 프록시 설정 없이 `X-Forwarded-For`·`Forwarded`가 붙은 어드민 요청은 404와 오류 로그(프로세스당 한 번)로 닫는다.
- 최초 Owner는 API 실행 인자 `--bootstrap-owner`로 `admin_users`가 비어 있을 때만 만든다.
- 2인 승인이 없으므로 작성자·승인자 분리도 없다. 지급 실행은 실행자 단독 승인(`self_approved=true`)으로 감사에 표시하고, 대상 2명 이상과 보정 지급은 실행 역할을 Admin으로 올려 위험을 줄였다.
- 남은 약점: 로그인 실패 응답은 하나지만 있는 로그인 이름만 실패 횟수 갱신 트랜잭션을 거쳐 처리 시간 차이로 이름 존재를 추정할 수 있다.

어드민 API 경로 초안과 구현 여부. 구현된 전체 경로·메서드·최소 역할 표는 [Backend README](../../Backend/README.md)의 "엔드포인트"이고 상수 원본은 `Backend/src/Shinshi.Contracts/Admin/AdminApiRoutes.cs`다.

| 경로 작업명 | 목적 | 구현(U25) |
|---|---|---|
| `GET /admin/v1/accounts?query=`, `GET /admin/v1/accounts/{id}` | 검색·상세 | 구현됨. `GET` 검색은 UUID만, 초대 코드 원문은 `POST /admin/v1/accounts/search` 본문으로. 상세는 `reason` 조회 문자열 필수 |
| `GET /admin/v1/ledger`, `GET /admin/v1/items/{id}/history`, `GET /admin/v1/sessions/{id}/events` | 로그 조회 | 구현됨(`reason` 필수, 조회 전 감사). `GET /admin/v1/operations/{actorId}/{operationId}`, `GET /admin/v1/audit` 추가 |
| `POST /admin/v1/grants`, `/grants/{id}/approve`, `/grants/{id}/execute`, `/grants/{id}/cancel` | 지급 작성·승인·실행·취소 | `approve` 없음(2인 승인 P1). 나머지와 `GET /grants/{id}` 구현됨. 대상 2명 이상·보정 지급의 `execute`는 Admin |

| `POST /admin/v1/invites` | 초대 코드 발급 | 구현됨. `POST /admin/v1/invites/{id}/revoke` 추가 |
| `PUT /admin/v1/service-state` | 점검 모드·기능 차단·허용 빌드 | 구현됨(`GET`도 있음) |
| `POST /admin/v1/notices`, `POST /admin/v1/events` | 공지·이벤트 | 공지만 구현(`GET`, `POST /notices/{id}/end` 포함). 이벤트 없음(P1) |

| `POST /admin/v1/accounts/{id}/sanctions`, `/kick` | 제재·강제 종료 | `kick`만 구현(기존 토큰·인증 묶음·초대 폐기, 현재 접속 유지, 비밀번호 로그인은 막지 않음). 제재 없음(P1) |

업무 변경 쓰기 경로는 모두 `operationId`와 `reason`이 필수다. 인증 경로(`/auth/login`은 자격 증명만, `/auth/logout`은 본문 없음)는 예외이며 operation 없이 단독 감사 행을 남긴다(4.3). 게임 클라이언트와 런처가 읽는 공지·서비스 상태는 일반 경로 `GET /v1/service-state`로 따로 제공한다. 플레이어 우편함은 일반 경로 `GET /v1/inbox`, `POST /v1/inbox/claim`(플레이어 접근 토큰)이다.

# 컨텍스트 관리

> 긴 세션과 대형 파일에서 AI가 잘못된 맥락으로 작업하지 않게 한다.

---

## 1. 읽기 전략

| 상황 | 방법 |
|---|---|
| 특정 기능을 찾을 때 | 심볼명 · 파일명으로 검색 → 해당 구간만 읽기 |
| 씬 파일 | **전체를 읽지 않는다.** 수십만 줄이고 대부분 무의미하다 |
| ScriptableObject 에셋 | 인스펙터 값이 필요하면 YAML을 직접 읽되 필요한 필드만 |
| 기획 문서 | 목차를 보고 해당 절만 |
| 로그 | 신규 에러부터. 기존 경고는 별도 분류 |

### 씬 파일을 읽어야 할 때

전체를 덤프하지 말고 원하는 오브젝트명이나 컴포넌트명으로 검색한다.
씬 구조를 파악해야 하면 Unity 에디터의 하이어라키를 캡처해 달라고 요청하는 편이 낫다.

---

## 2. 신뢰 순서

정보가 충돌하면 아래 순서로 판단한다.

1. **현재 코드와 설정** — 실행되는 것
2. **`git status` / `git diff`** — 지금 무엇이 바뀌었는지
3. **[`AGENTS.md`](../../AGENTS.md)와 협업 규칙** — 승인된 계약
4. **기획 문서** ([기획서](../02-game-design.md) · [기술설계서](../03-technical-design.md)) — 설계 의도
5. **이전 세션의 인수인계** — 과거 상태
6. **과거 대화의 상태 설명** — 현재 코드와 재대조

사용자의 최신 명시 지시는 상태 설명과 다르다. 권한·요구사항·우선순위를 정하므로 과거 코드나 문서로 무효화하지 않는다.

**기획 문서의 수치와 코드의 수치가 다르면 코드를 우선하고, 차이를 보고한다.**
밸런스 수치는 개발 중 계속 바뀐다. 문서가 뒤처지는 것이 정상이다.

---

## 3. 긴 세션 관리

세션이 길어지면 아래 신호를 확인한다.

| 신호 | 대응 |
|---|---|
| 앞서 읽은 파일 내용을 다시 확인해야 함 | 다시 읽는다. 기억에 의존하지 않는다 |
| 여러 파트를 동시에 건드리고 있음 | 작업을 분리한다 |
| 수정한 파일이 10개를 넘어감 | 변경 범위를 점검하고 검증한다. 커밋은 사용자 명시 요청이 있을 때만 한다 |
| 원래 요청이 무엇이었는지 흐릿함 | 작업 브리프를 다시 확인한다 |
| 대화가 길어 앞부분이 요약(압축)됨 | 요약은 손실이 있다. "하지 말 것" 제약과 예외 조건이 빠지기 쉬우므로 브리프와 규칙 원문을 다시 읽는다 |
| 여러 시간 · 여러 단계가 걸리는 작업 | 할 일 체크리스트를 개인 기록 위치(`.claude/docs/{날짜}/`)의 파일로 두고 끝난 항목을 표시하며 새로 찾은 일을 추가한다. 대화 기록 대신 이 파일로 진행 상태를 판단한다 |

**변경한 파일은 보고 전에 반드시 다시 읽는다.** 중간에 다른 편집이 있었을 수 있다.

---

## 4. 반복 작업

같은 파일을 여러 번 고칠 때는 매번 현재 내용을 다시 읽는다.
"아까 이랬으니 지금도 이럴 것"이라는 가정이 가장 흔한 오류 원인이다.

---

## 5. 검색 규칙

- 정확한 심볼명 · 파일명 · 설정 키를 먼저 검색한다
- 결과가 많으면 디렉터리와 확장자로 좁힌다
- 결과가 0이면 이름 변경, 경로 이동, 생성 코드 여부를 확인한다
- `.meta` 파일은 검색 결과에서 제외한다 (노이즈)
- `Library/`, `Temp/` 는 항상 제외한다

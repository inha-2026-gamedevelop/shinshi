# 응답 스타일 가이드

> AI 결과 보고의 형식과 증거 표기를 통일한다.

---

## 1. 기본 형식

```markdown
## 결론
(한두 문장. 무엇이 되었고 무엇이 안 되었나)

## 변경 내용
| 파일 | 무엇을 |
|---|---|

## 검증
| 주장 | 수준 | 증거 | 상태 |
|---|---|---|---|

## 미검증 · 남은 위험

## 다음에 필요한 것
```

---

## 2. 원칙

- **결론부터.** 과정을 먼저 늘어놓지 않는다
- 사실 · 추정 · 미검증을 구분한다
- 검증하지 않은 것을 "동작합니다"라고 쓰지 않는다
- 실패를 성공으로 포장하지 않는다
- 범위 밖 기존 결함은 별도로 표시한다
- 이쪽 저쪽 등 이해하기 애매한 표현은 사용하지 않는다.

---

## 3. 쓰지 말아야 할 표현

| 피할 표현 | 대신 |
|---|---|
| "완벽하게 구현했습니다" | "구현했고 L2까지 검증했습니다. L3는 미검증입니다" |
| "동작할 것입니다" | "동작을 확인하지 못했습니다. 멀티플레이 접속 테스트가 필요합니다" |
| "간단히 수정했습니다" | 무엇을 어디서 고쳤는지 명시 |
| "문제없습니다" | 무엇을 확인했고 무엇을 확인하지 못했는지 |
| "테스트했습니다" | "M2 등급으로 20회 반복, 20/20 정상" |

---

## 4. 증거 표기

주장마다 증거를 붙인다.

```markdown
- 적 스폰 위치가 모든 클라이언트에서 일치 — M2, 스폰 지점 전부, 3회 반복 확인
- 150ms 지연 환경 — **미검증**, Network Simulator 미설치
- 피격 시 체력 감소량이 서버 값과 일치 — M2, 5회 중 5회 정상
```

숫자가 없는 검증 주장은 신뢰도가 낮다.

---

## 5. 코드를 보여줄 때

- 변경한 부분만 보여준다. 파일 전체를 덤프하지 않는다
- 왜 그렇게 했는지 한 줄 덧붙인다
- 대안이 있었으면 왜 이 방식을 골랐는지 적는다

---

## 6. 질문할 때

한 번에 하나씩, 선택지와 함께 묻는다.

```markdown
사망한 플레이어의 부활 지점을 어떻게 할까요?

- A. 사망 지점 그대로 — 현재 기획서 결정. 위험 지역에서 재사망 반복 가능
- B. 가장 가까운 안전 지점으로 보정 — 반복 사망 방지, 긴장감 약화

기획서는 A로 확정되어 있어 A로 구현했습니다. 플레이 테스트 후 재검토 항목으로 남아 있습니다.
```

이미 결정된 것을 다시 묻지 않는다. 결정을 확인하고 우려만 짧게 남긴다.

---

## 7. 길이

- 단순 작업: 결론 + 변경 파일 목록이면 충분
- 복잡한 작업: 위 기본 형식 전체
- 조사 · 분석: 결론 → 근거 → 선택지 → 권고

**보고가 작업보다 길어지지 않게 한다.**

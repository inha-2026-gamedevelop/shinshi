# 멀티플레이 테스트 절차

> 2026-09-30 shinshi 기준으로 이식. 전투 파티 최대 인원은 4명, 호스트 방식은 데디케이티드 서버(확정)다.

> 멀티플레이 결함 대부분은 **단일 플레이에서는 멀쩡하고 여러 명이 접속했을 때만 깨진다.**
> 그래서 "실행해봤다"는 검증 증거가 되지 못한다. 무엇을 어떻게 확인했는지가 필요하다.

---

## 1. 테스트 등급

| 등급 | 구성 | 언제 |
|---|---|---|
| M0 | 단일 인스턴스 (에디터 호스트 모드 혼자) | 컴파일 확인, 로컬 로직 |
| M1 | 서버 + 클라 1 (같은 PC, ParrelSync 또는 빌드) | 동기화 기본 확인 |
| M2 | 서버 + 클라 2 이상 (같은 PC) | 여러 명 로직, 공유 자원 |
| M3 | 서버 + 클라 2 이상 (**서버와 클라가 서로 다른 PC**) | 실제 지연 환경 |

**네트워크가 걸린 변경은 최소 M2다.** M0에서 되는 것은 증거가 아니다.
인원이 결과에 영향을 주는 로직(전원 조건, 정원, 동시 요청)은 4명을 모두 채워서 확인한다.

지연 보상, 짧은 타이밍 판정, 투사체 동기화는 **M3까지 확인**한다. 같은 PC에서는 지연이 0에 가까워 문제가 드러나지 않는다.

위 표의 "서버"는 플레이어 없이 판정만 하는 서버 전용 인스턴스다 (에디터 `Server Only` 또는 Dedicated Server 빌드). **M1 이상에서 서버를 호스트 모드로 대신하지 않는다.** 호스트 모드는 서버와 클라이언트를 한 프로세스에서 겸해 SyncVar 훅 · Rpc가 서버에서도 불리므로, 서버 전용 경로의 결함을 숨긴다.

**M3의 서버는 한 PC로 고정한다.** 서버가 바뀌면 틱 · 프레임 측정치를 이전 회차와 비교할 수 없다. 실제 호스팅 환경이 정해지면 그 사양에 맞춘다.

## 2. 같은 PC에서 여러 인스턴스 띄우기

### 2.0 현재 실행 도구

- [`tools/Start-M2.ps1`](../../tools/Start-M2.ps1)은 미리 만든 Windows 전용 서버와 클라이언트 N개를 실행한다. 빌드는 만들지 않는다. `ClientCount 1`은 M1, 2 이상은 M2 구성이고 프로세스 기동만으로 접속·동작 통과를 판정하지 않는다.
- [`tools/Start-ReleaseStack.ps1`](../../tools/Start-ReleaseStack.ps1)은 로컬 PostgreSQL·마이그레이션·API·마을 서버·개발 클라이언트를 실행한다. `-Build`를 지정할 때만 Unity 빌드를 만들며 이때 에디터를 닫아야 한다. 던전 서버도 `-DungeonCount`(기본 1)만큼 띄우고, 출정 1회가 끝나 던전이 종료되면 `tools/Watch-ReleaseDungeons.ps1`이 같은 인스턴스 ID로 새로 띄운다. 이 스택은 로컬 리허설용이며 운영 서버 풀 확장과 장애 복구 시험이 아니다.
- 에디터 [`ShinshiPlayMenu`](../../Assets/Editor/ShinshiPlayMenu.cs)의 `Shinshi/Play/` 메뉴는 에디터의 역할·접속 실행을 담당한다. 위 PowerShell 스크립트와 같은 도구로 간주하지 않는다.
- 빌드 경로·필수 환경과 실행 예시는 [루트 안내](../../README.md), [게임 서버 안내](../../deploy/gameserver/README.md)를 따른다. 개발 토큰 우회로 하는 이동 시험과 API 입장 토큰을 검증하는 실제 출정을 구분한다.

**시작 전에 확인할 것.** 하나라도 어긋나면 여러 명 검증이 성립하지 않는다.

| | 왜 |
|---|---|
| ✅ **개발용 빌드가 최신인가** | 실행 인자 파싱을 `DEVELOPMENT_BUILD`로 감싸면 릴리스 빌드는 인자를 무시한다 |
| ✅ **개발용 최소 인원 설정이 테스트 인원과 맞는가** | 1로 두면 첫 클라이언트 혼자 게임이 시작되면서 입장이 잠겨 나머지가 거부될 수 있다 |
| ✅ **한 PC 여러 창에서 커서 잠금을 끄는가** | 끄지 않으면 창 하나가 마우스를 독점해 나머지 창이 카메라를 못 돌린다 |
| ✅ **테스트할 씬에 대상이 있는가** | 아래 2.0.1 |

#### 2.0.1 테스트 씬과 검증 범위

`Bootstrap`, `Dev_PlayerMovement`, `Dev_AI/`, `Dev_HUD/`와 `Release/` 실행 씬이 존재한다. `Dev Test` 빌드의 보스·UI 단독 시험과 실제 접속 씬을 구분한다. 개발 씬이 있다는 사실은 M2 실행 증거가 아니다. 멀티플레이 검증용 씬을 만들 때 아래를 따른다.

- 검증 대상(적, 아이템 등)은 스포너보다 **씬에 직접 배치**한다. 게임 진행 상태에 의존하지 않아야 서버를 켤 때마다 같은 자리에 있고, 테스트가 재현된다.
- 씬마다 무엇이 있는지(대상, 카메라, 빌드 목록 포함 여부, 쓰임)를 표로 적는다.
- 구운 NavMesh 에셋은 씬과 함께 커밋한다.

### 방법 A — ParrelSync

프로젝트를 심볼릭 링크로 복제해 에디터를 여러 개 띄운다. (설치 전)

- 장점: 코드 수정이 즉시 반영됨, 브레이크포인트 사용 가능
- 단점: 초기 세팅 필요, 에디터 여러 개가 메모리를 많이 씀

### 방법 B — 빌드 + 에디터

에디터를 서버(`Server Only`)로, 빌드된 실행 파일을 클라이언트로 띄운다. 또는 서버 빌드를 띄우고 에디터를 클라이언트로 붙인다.

- 장점: 세팅 불필요, 실제 빌드 동작 확인
- 단점: 코드 수정 때마다 재빌드

### 방법 C — Unity Multiplayer Play Mode

Unity 6의 기능. 한 에디터에서 여러 플레이어를 시뮬레이션한다. (설치 전)

- 장점: 가장 빠름
- 단점: 실제 네트워크 스택을 완전히 재현하지 않음

**현재 실행 기준**: B 또는 위 실행 스크립트로 전용 서버와 클라이언트를 확인한다. A·C는 설치·Mirror 호환 확인 후 사용할 대안이며 현재 검증 기반으로 가정하지 않는다.

## 3. 지연 환경 재현

같은 PC에서는 지연이 0이라 지연 관련 결함이 드러나지 않는다.

| 도구 | 용도 |
|---|---|
| Mirror `LatencySimulation` | 트랜스포트를 감싸 지연 · 패킷 손실 주입 |
| Clumsy (Windows) | OS 레벨에서 네트워크 조건 조작 |

### 확인할 조건

| 조건 | 지연 | 패킷 손실 |
|---|---|---|
| 이상적 | 0ms | 0% |
| 지연 비교 | 50ms | 0% |
| 지연 상한 비교 | 150ms | 0% |
| 손실 비교 | 0/50/150ms | 1% 및 3% |

[로드맵](../05-implementation-roadmap.md)의 0/50/150ms·손실 1%/3% 조건을 따른다. 지연은 편도 주입값인지 RTT인지 기록한다. `DevLatencyFromArgs`는 송신 지연을 넣으므로 양쪽에 같은 값을 주면 왕복 지연은 그 합이다. 판정 창이 짧은 입력은 조건별로 최소 10회 반복하며, 손실 설정·실제 적용 여부도 별도로 확인한다.

## 4. 시나리오별 체크리스트

아래는 공통 체크리스트다. 신시의 실제 수용 범위는 [로드맵](../05-implementation-roadmap.md)의 작업별 관찰·배포 기준과 함께 사용한다. 기존 예시만 통과했다고 신규 직업·일반전·경제 전체를 검증한 것으로 세지 않는다.

### 접속 · 세션

- [ ] 서버 시작 후 클라이언트가 순차 접속된다
- [ ] `{최대 인원}`을 넘는 접속은 거부된다
- [ ] 클라이언트 1명이 나가도 나머지가 계속 진행된다
- [ ] 모든 클라이언트가 나가도 서버가 크래시 없이 다음 세션을 받을 수 있다
- [ ] 서버가 종료되면 클라이언트가 크래시 없이 끊김을 처리한다
- [ ] 재접속 시 상태가 어긋나지 않는다

### 전투 · 피격

- [ ] 여러 명이 동시에 같은 적을 때려도 HP가 정확히 깎인다
- [ ] 피격 판정 결과가 모든 클라이언트에서 같게 보인다
- [ ] 투사체 궤적이 모든 클라이언트에서 같게 보인다
- [ ] 투사체가 벽에 막혀 뒤의 대상을 맞히지 않는다
- [ ] 타이밍 판정이 모든 화면에서 같은 결과를 낸다 — 서버 시각 기준 판정이면 RTT가 달라도 성공/실패가 일치해야 한다

### 아이템 · 경제

- [ ] 드랍된 아이템을 두 사람이 동시에 주우면 한 명만 획득한다
- [ ] 공용 재화가 모든 클라이언트에서 같은 값으로 보인다
- [ ] 두 사람이 동시에 구매해도 잔액이 음수가 되지 않는다
- [ ] 아이템 양도 시 원 소유자에게서 정확히 사라진다

### 공유 상태 · 시간

- [ ] 서버가 정하는 공유 값(제한 구역, 단계, 진행도 등)이 모든 클라이언트에서 같다
- [ ] 서버 이벤트 알림(경고, 단계 전환)이 모든 클라이언트에 동시에 뜬다
- [ ] 특정 플레이어에게만 가야 할 결과가 그 플레이어에게만 적용된다
- [ ] 게임 내 시간이 모든 클라이언트에서 같게 표시된다

### 사망 · 부활

- [ ] 부활 타이머가 모든 클라이언트에 같게 보인다
- [ ] 부활 비용이 정확히 한 번만 차감된다
- [ ] 부활 직후 보호 효과가 한 번만 적용된다
- [ ] 전원 사망 같은 전체 조건이 타이밍 차이로 오판정되지 않는다

### 적 · AI

- [ ] 적의 상태 전환이 모든 클라이언트에서 동시에 일어난다
- [ ] 공격 예고 표식이 모든 클라이언트에서 같은 위치에 뜬다
- [ ] 적 스폰 · 사망이 모든 클라이언트에 반영된다

### 서버 부하

데디케이티드 서버 한 대가 전원의 판정을 진다. 부하가 한계를 넘는지는 **측정하지 않으면 알 수 없다.** M3 통합 테스트마다 기록한다.

- [ ] 동시 오브젝트(적, 투사체)가 가장 많은 구간(최종 웨이브 등)에서 서버 틱 · 프레임을 측정했다
- [ ] 같은 구간의 클라이언트 프레임을 따로 측정했다 (서버는 렌더링이 없으므로 서버가 느리면 판정 로직부터 의심한다)
- [ ] **타이밍 판정 성공률을 지연 조건별로 집계했다** (각 20회 이상)
- [ ] 성공률이 체감할 수준으로 낮으면 판정 창 조정을 검토했다

#### 프레임을 잴 때 먼저 맞출 조건

**이 조건을 안 맞추면 측정값을 서버 비용 판정에 쓸 수 없다.** 한 PC 여러 창에서는 서버 틱 저하처럼 보이는 현상이 실제로는 같은 PC의 클라이언트 렌더링과 자원을 다툰 결과인 경우가 있다.

- [ ] 모든 인스턴스에 **같은 FPS 상한**이 걸려 있다
- [ ] 모든 인스턴스의 **해상도가 같다** — 빌드는 실행 인자 `-screen-width 1280 -screen-height 720 -screen-fullscreen 0`으로 고정한다
- [ ] 모든 인스턴스의 **품질 설정이 같다**
- [ ] 서버도 **에디터가 아니라 서버 빌드**로 실행했다 — 에디터 비용이 얹히면 서버 비용을 판정할 수 없다
- [ ] 서버 비용을 최종 판정할 때는 **M3(서로 다른 PC)** 로 다시 잰다

같은 PC에서 위 조건 없이 잰 서버/클라이언트 수치는 **기능 검증에는 쓰되 성능 판정에는 쓰지 않는다.**

## 5. 검증 기록 형식

PR이나 보고에 아래 형식으로 남긴다.

```markdown
### 멀티플레이 검증

- 등급: M2 (서버 + 클라 2, 같은 PC, ParrelSync)
- 지연 조건: 0ms
- 확인 항목:
  - [x] 아이템 동시 획득 시 한 명만 획득 — 20회 중 20회 일치
  - [x] 피격 판정이 양쪽에서 같음 — 20회 중 20회 일치
  - [ ] 150ms 지연 환경 — **미검증** (지연 시뮬레이션 미설정)
- 서버 틱 / 클라 평균 프레임: 최대 부하 구간 __ / __ fps
- 타이밍 판정 성공률: 0ms __ / 20, 150ms __ / 20
- 관찰된 문제: 없음
- 남은 위험: 실제 지연 환경 미확인
```

**"여러 명으로 테스트했습니다"만으로는 증거가 되지 않는다.** 무엇을 몇 번 확인했는지 적는다.

## 6. 자주 놓치는 것

| 함정 | 증상 |
|---|---|
| 호스트 모드에서만 테스트 | 호스트 모드는 지연 0이고 서버에서도 훅 · Rpc가 불려 서버 전용 결함을 숨긴다. 서버 전용 인스턴스 + 클라이언트로 반드시 확인 |
| 1회만 확인 | 타이밍 결함은 확률적으로 나타난다. 최소 10회 반복 |
| 순차 실행만 확인 | 동시 실행(동시 획득, 동시 구매)이 실제 결함 지점 |
| 정상 경로만 확인 | 접속 끊김, 사망 중 이벤트 발생 같은 경계 상황 |
| 시각적 일치만 확인 | 보이는 게 같아도 내부 값이 다를 수 있다. 로그로 값을 찍어 비교 |

## 7. 주간 통합 테스트

매주 정해진 요일에 아래를 실행한다.

1. 각자 `feature/{팀원이름}` 브랜치를 통합 브랜치 `develop`에 병합
2. 통합 담당자가 통합 씬에 반영
3. **빌드해서 여러 명 접속** (M3 — 서로 다른 PC)
4. 위 체크리스트 중 이번 주 변경과 관련된 항목 실행
5. 실패 항목을 그 자리에서 이슈로 등록

마감 직전에 없는 기능을 발견하면 손 쓸 방법이 없다. 주간 테스트는 이를 조기에 발견하기 위한 장치다.

## 8. 플랫폼 트랜스포트 테스트 (도입 예정)

트랜스포트는 (미정)이다. Steam P2P 같은 플랫폼 트랜스포트를 도입하면 **같은 PC·같은 계정으로 검증할 수 없는 경우가 많다.** 자기 자신에게 연결하면 실패한다.
그런 트랜스포트의 변경은 M2를 건너뛰고 바로 M3로 확인한다. 도입할 때 준비물, 참가 경로, 막혔을 때 보는 곳을 이 절에 적는다.

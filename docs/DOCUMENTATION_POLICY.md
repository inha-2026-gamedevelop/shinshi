# 문서 분류와 현재성 기준

2026-09-30 shinshi 기준으로 이식. 문서는 현재 코드·설정과 팀이 합의한 요구사항을 구분한다.

## 어디에 남기는가

기존 공용 읽기 안내·게임 기획·기술 설계·사용 문서는 공용 정본으로 유지한다. 특정 작업자의 설계 노트·작업 결과·실행 증거만 개인 기록으로 분리한다. 공용 문서 전체를 개인 영역으로 옮기지 않는다.

| 독자와 내용 | 위치 |
|---|---|
| 팀 전체가 지켜야 할 계약, API, 게임 규칙, 실행 방법, 검증 절차, 담당자 인계 | `docs/` |
| 특정 실행자의 세션 기록, 개인 모델 선호, 개인 PC 설정, 계정 잔액·배포 자원 기록, 시행착오와 원시 증거 | Git 제외 개인 기록 영역 |
| 실행 도구 바로 옆의 사용 안내 | 해당 도구·서비스 폴더의 README (`Backend/`, `Launcher/`, `Web/`, `deploy/` 등). 팀 문서에서 연결 가능하며 실제 존재하는 경로만 안내한다 |
| 아직 구현하지 않은 팀 기획 | `docs/`에 제안/목표임을 명시. 현재 구현과 별도 절로 분리 |

개인 기록의 실제 저장 경로와 시작 방법은 저장소 루트의 에이전트 지침에서 관리한다. 공유 문서에 개인 기록을 읽어야 이해되는 문장이나 그 기록의 링크·파일 경로를 남기지 않는다.

## 팀 문서가 자립하려면

- 규칙의 근거는 실제 코드·SO·버전 관리되는 테스트와 팀 문서에서 찾을 수 있어야 한다.
- 개인 로그에만 있던 결론이 필요하면 결과, 날짜, 실행 조건, 한계를 팀 문서 본문에 적는다. 비공개 원시 로그를 필독 대상으로 삼지 않는다.
- 비밀값, 계정 식별자, 개인 키 위치, 비용 잔액과 개인 도구 제한은 팀 문서에서 제외한다. 공개 API 주소처럼 협업에 필요한 값은 실제 설정의 위치로 안내한다.
- 과거 성공 기록은 당시 버전의 결과다. 현재 코드에 대한 새로운 실행 검증으로 표시하지 않는다.
- 코드는 존재하지만 실행 검증을 하지 않았다면 `구현됨·실행 미검증`으로 적는다. 계획과 실제 동작이 다르면 양쪽을 분리한다.
- 파일 이동 시 들어오는 링크와 나가는 링크를 모두 수정한다. 개인 문서로 옮긴 자리에 개인 경로를 가리키는 공유 포인터를 남기지 않는다.
- 팀에 필요한 내용과 개인 기록이 섞였으면 공유 계약을 남기고 개인 실행 기록만 분리한다.

## 갱신 순서

1. 요청 범위의 코드·설정·데이터와 기존 미커밋 변경을 확인한다.
2. 옛 문서의 구현 없음/계획/현재 주장과 실제 진입점·호출·데이터를 대조한다.
3. 현재 계약은 본문에서 고친다. 오래된 본문을 남긴 채 머리말만 최신이라고 덧붙이지 않는다.
4. 링크와 인덱스([AI 작업 문서](ai/README.md), [프로젝트 지식 맵](ai/07_PROJECT_KNOWLEDGE_MAP.md))를 함께 갱신한다.
5. 이번 정적 검수와 과거 런타임 검증을 구별해 보고한다.

# 도입 기능 계획

> 기준일: 2026-10-01 · 상태: **제안(미구현)** · 담당: 민성 · 대상: 공통·전투·서버·개발 도구 작성자
> 언리얼 엔진의 게임플레이 구조와 이전 프로젝트의 개발 도구 중 신시에 가져올 것을 정리한 제안이다. 여기 적은 타입·파일·패널은 아직 코드에 없다. 도입이 결정되면 계약은 [기술설계서](../03-technical-design.md)와 [아키텍처](../04-architecture.md) 본문으로 옮기고 이 문서에서는 링크만 남긴다.

## 1. 목적과 판단 기준

Unity에 내장되어 있지 않지만 신시 설계가 이미 요구하고 있는 기능을 **엔진 전체가 아니라 필요한 구조만** 가져온다. 도입 근거는 [디자인 패턴](DESIGN_PATTERNS.md) 0장의 세 가지 중 하나여야 한다.

| 근거 | 이 문서에서의 예 |
|---|---|
| 지금 있는 중복을 없앤다 | 12기술·부적 45효과·수련·장비 보정이 각자 수치 계산 경로를 만드는 것 |
| 되돌리면 깨지는 순서를 고정한다 | 서버 거절 시 클라이언트가 먼저 보여 준 쿨다운·기력을 되돌리는 순서 |
| 아직 없는 파트를 기다리지 않게 한다 | 헤드리스 서버의 판단을 화면 없이 확인하는 창구 |

렌더링 기능(Nanite, Lumen, MetaHuman, World Partition)은 대상이 아니다. 스타일화 URP와 1~4인 전장 규모에서 얻는 것보다 비용이 크다.

## 3. A01 개발 웹 패널

### 3.1 왜 웹 패널인가

- Unity 플레이어는 자기 프로세스에서 두 번째 OS 창을 열 수 없다. 게임 화면 위에 IMGUI로 그리면 전투 화면을 덮는다.
- 신시 서버는 Linux 헤드리스라 화면이 아예 없다. 프로세스가 HTTP 포트를 열고 브라우저로 들여다보는 방식이 서버 상태를 보는 가장 짧은 경로다.
- 콘솔 변수(CVar)와 둘 중 하나를 고르는 문제가 아니다. 패널의 명령 등록소가 곧 CVar 역할을 하고, 웹 페이지는 그 위의 조작 화면이다.

### 3.2 이전 프로젝트 개발 도구에서 가져올 것

이전 프로젝트 `Assets/01.Scripts/99.Dev/`의 구현을 참고해 `Shinshi.Dev`로 다시 작성한다. 웹 서버·패널 기반은 `Shinshi.Dev` 어셈블리에, 서버 패널(던전·마을)은 `Shinshi.Server` 안에 두고 `Shinshi.Dev`를 참조한다. 로그·기즈모 호출 API는 도메인 코드가 부르므로 `Shinshi.Runtime`에 `[Conditional]`로 둔다([코딩 컨벤션](../coding-convention.md) 0장). 다음 설계는 그대로 유지한다.

| 구성 | 역할 | 유지할 설계 |
|---|---|---|
| `DevWebServer` | 로컬 HTTP 서버 | `HttpListener` 대신 `TcpListener` 사용(Windows URL ACL 관리자 권한 문제 없음, Linux 동작). 배경 스레드에서 수신. 요청 헤더 8KB·본문 64KB 제한. 소켓 시간 제한 |
| 보안 | 외부 조작 차단 | 기본 루프백만 수신. 실행마다 무작위 토큰을 페이지에 넣고 `POST`는 토큰 헤더를 요구(다른 사이트의 위조 요청 차단). `Host` 헤더가 IP나 `localhost`가 아니면 거절(DNS 리바인딩 차단) |
| `DevPanelHost` | 패널 등록·상태 JSON·명령 적용 | 배경 스레드가 받은 명령은 큐에 넣고 메인 스레드 `Update`에서 적용(Unity API는 메인 스레드 전용). 큐 상한 |
| `DevPanel` | 조작 정의 | `DevPanelBuilder`로 버튼·토글·슬라이더·선택을 선언. 선택 조작은 라벨이 아니라 순번을 보낸다 |
| `DevWebPage` | 브라우저 화면 | `GET /api/state`를 주기적으로 읽고, `POST /api/command`로 `{panel, control, value}`를 보낸다 |
| 포트 | 여러 인스턴스 | 인자로 받은 포트가 쓰이고 있으면 다음 번호로 올려 잡는다 |

### 3.3 신시에서 바꿀 것

**권위 위치가 다르다.** 이전 프로젝트는 호스트가 곧 서버라 호스트 PC 패널에서 권위 상태를 바로 바꿨다. 신시 클라이언트는 권위가 아니므로 패널을 프로세스 역할로 나눈다.

| 패널이 뜨는 곳 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| 클라이언트 | 로그, 기즈모·콜라이더 표시, 카메라 값, 프레임·RTT·입력 거절 수, 스크린샷·커서 | 체력·자원·쿨다운·스폰·시간 배속 변경 |
| 던전 서버 | 세션 단계·참가자·생사·부활 잔여 조회, 웨이브 건너뛰기·스폰 정지, 월백 페이즈·패턴 지정, 참가자 지정 무한 체력·기력·쿨다운 0, 서버 시간 배속, A05 기록 조회 | 재화·아이템·티켓 지급 |
| 마을 서버 | 접속자·영역별 인원, 채집 노드 상태, 출정 대기열·던전 풀 상태, 경매 상태 | 재화·아이템·티켓 지급 |

- 서버 패널의 조작도 서버 코드의 일반 판정 경로를 거친다. 예를 들어 "무한 체력"은 피해 계산을 건너뛰는 분기가 아니라 대상 참가자에게 개발 전용 상태를 붙이고, 피해 규칙이 그 상태를 읽게 한다. 판정 코드에 `if (dev)` 분기를 흩뿌리지 않는다.
- 클라이언트 패널에서 서버 조작을 보내는 경로(Mirror dev Command)는 초기 범위에서 제외한다. 필요해지면 서버가 개발 빌드 여부와 요청 연결의 개발 권한을 검증하는 별도 작업으로 연다(5장).

**재화·아이템 지급은 패널이 직접 하지 않는다.** DB는 API만 쓰고 모든 잔액 변경은 경제 원장(U24)을 거친다. 개발 지급은 개발 환경에서만 켜지는 API 엔드포인트나 운영 어드민(U25)의 지급 기능으로 처리하고, 원장 사유를 남긴다. 패널에는 그 API를 부르는 버튼까지만 둔다.

**출시 빌드 잠금 해제 방식은 가져오지 않는다.** 이전 프로젝트는 릴리스 빌드에 도구를 넣어 두고 키 순서로 열었다. 신시는 외부 체험판에서 개발 명령을 제거해야 하므로([기술설계서](../03-technical-design.md) 13장) 도구 전체를 컴파일에서 뺀다.

### 3.4 빌드 제거

- `99.Dev/`의 도구 전체를 `#if UNITY_EDITOR || DEVELOPMENT_BUILD`로 묶는다. 외부 체험판 클라이언트·서버는 Development Build를 끄고 빌드하므로 타입 자체가 없다.
- 로그·기즈모 호출부는 `[Conditional]` 특성으로 외부 빌드에서 호출까지 사라지게 한다.
- 개발 빌드가 아닌 내부 성능 측정 빌드에도 도구가 필요한지는 미정이다(5장). 필요하면 별도 스크립팅 정의를 두되 외부 체험판 빌드 프로필에는 넣지 않는다.

### 3.5 서버 실행 규칙

- 포트는 실행 인자로 받는다. 던전 풀은 한 머신에 프로세스 여러 개가 뜨므로 풀 번호로 포트를 나눈다.
- 패널 맨 위에 프로세스 역할(`client`/`town`/`dungeon`), 던전 풀 번호, sessionId, contentVersion, buildId를 표시한다. 여러 창을 열어 두고 구분하는 용도다.
- AWS 서버의 패널은 루프백에만 연다. 외부 개방 옵션을 쓰지 않고, 보안 그룹에 패널 포트를 열지 않는다. 접속은 SSH 터널이나 관리형 포트 포워딩으로 한다.
- 헤드리스 서버의 메인 스레드는 `sendRate`(30Hz) 주기로 돈다. 명령 적용은 다음 틱까지 지연될 수 있다.
- 종료 시 수신 스레드를 정리한다. 스레드를 남기면 에디터 플레이 종료가 붙잡힌다.

### 3.6 수용 기준

1. 에디터·개발 빌드 클라이언트 1개와 개발 빌드 던전 서버 1개가 각자 패널을 띄우고, 브라우저에서 역할 표시로 구분된다.
2. 토큰 없는 `POST`와 도메인 이름 `Host` 요청이 거절된다.
3. 서버 패널의 웨이브 건너뛰기·월백 페이즈 지정이 두 클라이언트 화면에 복제로 반영된다.
4. 외부 체험판 빌드 프로필로 만든 클라이언트·서버에서 패널 포트가 열리지 않고 `Shinshi.Dev` 타입이 어셈블리에 없다.

## 4. 게임플레이 구조

### 4.1 A02 데이터 검증

- [아키텍처](../04-architecture.md) 6장은 ID 중복·누락·효과 범위·불가능한 참조를 빌드 전에 검증하도록 요구한다. 현재 SO는 필드별 `OnValidate`와 `GameDB` 초기화 시 필수 참조 검사만 있다.
- 모든 정의 SO가 검증 인터페이스(예: `IDataValidatable`)를 구현하고 오류 목록을 돌려준다. 카탈로그 간 참조(부적 → 기술 ID, 웨이브 → 적 ID)는 `GameDatabaseSO`가 전체를 모아 검사한다.
- 같은 검증기를 세 곳에서 부른다. 에디터 메뉴(수동), EditMode 테스트(U22), 빌드 전처리(실패 시 빌드 중단).
- `OnValidate`는 값 범위 보정에만 쓰고 카탈로그 간 검증은 넣지 않는다. 에셋마다 불려 순서가 보장되지 않는다.

### 4.2 A03 게임플레이 태그

- **문제**: 서버 입력 검증의 "행동 제한", 보스 제어 허용 구간, 부적의 직업·기술·선택 단계 대상 지정은 모두 "이 개체가 이 부류의 상태를 가졌는가"를 묻는다. 닫힌 `enum` 조합으로 풀면 조합마다 분기가 늘어난다.
- **형태**: `Status.Control.Stun`, `Skill.Warrior.Cleave`처럼 점으로 구분한 계층 이름이다. 상위 태그 질의(`Status.Control` 아래 전부)를 지원한다.
- **저장**: 태그 정의는 SO 레지스트리에 둔다. 이름 변경을 ID 변경으로 취급하지 않는 [아키텍처](../04-architecture.md) 6장 정책을 따르고, 네트워크에는 레지스트리 순번(정수)을 보낸다. 순번 표는 contentVersion과 함께 버전 검사한다.
- **`enum`과 경계**: 코드가 분기하는 닫힌 집합(`ESessionState`, `EItemGrade` 등)은 계속 `enum`이다([코딩 컨벤션](../coding-convention.md)). 태그는 기획 데이터가 늘리는 열린 집합에만 쓴다.
- **보관**: 개체의 태그 집합은 서버가 소유하고, 클라이언트 표시에 필요한 태그만 복제한다.

### 4.3 A04 능력치·효과 명세·연출 큐

GAS 전체를 옮기지 않는다. [기술설계서](../03-technical-design.md) 14장 ADR03이 무거운 프레임워크를 피하기로 했으므로 아래 네 가지 구조만 가져온다.

| 구조 | 신시 적용 | 근거 |
|---|---|---|
| 능력치 + 수정자 | HP·기력·공명·공격력 등 능력치에 "기본값 + 가산 + 배율" 수정자를 출처(수련·장비·부적·상태)별로 쌓고 한 경로로 계산한다 | 네 성장 계통이 같은 능력치를 건드린다 |
| 효과 명세 | [아키텍처](../04-architecture.md) 6장의 "원본 기술 → 핵심 변형 → 보조 효과 → 레벨 보너스 → 최종 명세" 컴파일 결과를 불변 객체로 만든다. 서버 판정과 클라이언트 예고가 같은 명세 ID/hash를 쓴다 | 이미 요구된 계약 |
| 연출 큐 | 서버 결과 이벤트의 태그를 받아 `TelegraphPresenter`·`CombatFxPresenter`를 고르는 레지스트리. `eventId` 중복 차단과 늦은 접속 스냅샷은 [기술설계서](../03-technical-design.md) 4.3을 따른다 | 로직과 표현 분리 |
| 예측 되돌림 | 클라이언트가 기술 입력 직후 쿨다운·기력 소모를 **표시로만** 먼저 반영하고, 서버가 그 `inputSequence`를 거절하면 되돌린다. 새 예측 키를 만들지 않고 기존 입력 순번을 키로 쓴다 | 거절 시 자원 미소모 규칙([기술설계서](../03-technical-design.md) 4.2)을 표시까지 일관되게 |

- 피해·명중·보상은 예측하지 않는다. 예측 대상은 소유 캐릭터의 이동과 자기 쿨다운·자원 표시뿐이다.
- [디자인 패턴](DESIGN_PATTERNS.md) 4장은 수정자 체인을 "수정자 종류와 수치가 기획으로 정해진 뒤" 넣도록 했다. [전투 기준안](../design/combat-design.md)과 [성장·경제 기준안](../design/growth-economy.md)에 수정자 종류가 정의되어 있으므로, U05 착수 전에 수정자 목록을 뽑아 이 조건이 충족됐는지 확인하고 디자인 패턴 문서를 함께 고친다.

### 4.4 A05 서버 판단 기록기

- **문제**: 월백 패턴은 "기본 × 거리 × 방향 × 인원 × 최근 패턴" 가중 무작위라 왜 그 패턴이 나왔는지 재현하기 어렵다. 판정은 헤드리스 서버에서 일어나 에디터에서도 보이지 않는다.
- **형태**: 개발 빌드 서버가 틱 번호와 함께 기록 항목을 고리 버퍼에 쌓는다. 항목은 분류, 대상 netId, 도형(구·상자·부채꼴·선), 글자, 값 목록이다.
- **월백 선택 기록**: 선택 대상, 거리·방향, 5m 안 인원, 패턴별 가중치 구성 요소, 난수 값, 선택 결과.
- **판정 기록**: 공격 판정 도형, 적중 대상, `HitLedger` 중복 차단 여부.
- **개체 상태 조회**(Gameplay Debugger 대응): 서버 패널에서 netId로 개체 하나를 고르면 현재 태그 집합(A03), 능력치 최종값과 수정자 출처별 내역, 적용 중인 효과 명세(A04), 쿨다운, AI 상태 전이 단계를 보여 준다. 고른 개체는 클라이언트 기즈모에 표시해 화면에서 어느 개체인지 찾는다.
- **표시**: A01 서버 패널에서 최근 기록을 표로 보고, 클라이언트 기즈모로 도형을 월드에 그린다. 세션 종료 시 파일로 떨어뜨려 에디터 창에서 틱 단위로 되감아 보는 기능은 두 번째 단계로 둔다.
- 기록은 [기술설계서](../03-technical-design.md) 13장의 서버 로그(구조화 JSON)와 별개다. 운영 로그에 매 틱 판단을 섞지 않는다.

## 7. 이 문서를 갱신할 때

- 항목을 구현하면 요약 표의 상태를 바꾸는 대신 계약을 [기술설계서](../03-technical-design.md)·[아키텍처](../04-architecture.md)·[코딩 컨벤션](../coding-convention.md)의 해당 절로 옮기고, 여기에는 "도입됨"과 링크만 남긴다.
- 패턴을 코드에 넣으면 [디자인 패턴](DESIGN_PATTERNS.md) 2장 "적용 위치"를 채운다.
- 5장의 결정이 나면 해당 행을 지우고 본문에 반영한다.

## 1. 판단 기준은 하나다

> **이 값이 사람마다 달라도 게임 결과가 같은가?**

- 같다 → 클라이언트가 각자 계산한다
- 다르다 → 서버가 판정하고 결과를 보낸다

조명이 A의 화면에서 조금 더 어두워도 아무도 죽지 않는다.
히트박스가 다르면 A에서는 맞고 B에서는 안 맞는다.

## 3. 클라이언트가 각자 하는 것

| 영역 | 항목 |
|---|---|
| 렌더링 | 조명, 스카이박스, 안개, 포스트프로세싱 |
| 이펙트 | 파티클, 히트 이펙트, 트레일 |
| 카메라 | 위치, 셰이크, 줌, 컷신 재생 — ⚠️ **조준 대상처럼 남에게 보이거나 판정에 들어가는 것은 아래 3.1** |
| 애니메이션 | 블렌딩, 레이어 가중치 |
| 사운드 | 재생, 믹싱 |
| UI | 체력바 보간, 미니맵 그리기, 알림 |
| 성능 | LOD, 오클루전 컬링 |

### 3.1 로컬로 보이지만 로컬이 아닌 것

카메라·조준 기능은 로컬로 분류하기 쉽다. 하지만 그 결과가 **남의 화면에 보이거나 판정에 들어가면** 권위가 달라진다. 항목을 쪼개서 판단한다. 예: 대상 고정(조준 대상 선택) 기능.

| 항목 | 권위 | 왜 |
|---|---|---|
| 대상 **선택** 입력 | 로컬 | 누구를 고를지는 본인이 정한다 |
| 고정 여부 + **바라보는 방향** | **동기화** | 남의 화면에서 그 사람이 옳은 방향을 봐야 다른 사람이 상황을 읽는다 |
| 대상에 의존하는 판정 (예: 유도 투사체) | **서버** | 궤적이 대상에 의존하므로 판정이다 |
| 고정 UI (마커 · 화살표) | 로컬 | |

처음에 "순수 로컬 표현"으로 분류했다가 표현과 판정 양쪽에 들어가는 것으로 드러나는 일이 흔하다. 기능이 늘 때마다 다시 판단한다.

> 🔒 **서버가 검증할 것** — 요청한 `netId`의 실재 · 대상 생존 · 허용 거리 · 요청자 생존, 그리고 **판정 시점에 대상이 아직 유효한가**.
> 검증이 없으면 클라이언트가 맵 반대편 대상을 골라 판정을 조작할 수 있다.

## 4. 파생 계산 원칙

서버는 **원본 값 하나만** 보낸다. 표현은 클라이언트가 만든다.

| 서버가 보내는 것 | 클라이언트가 만드는 것 |
|---|---|
| 경과 시간 `900` | 게임 내 시각, 조명 프리셋, 스카이박스, 안개 색 |
| 제한 구역 반경 `120` | 경계 셰이더, 미니맵 원, 경계 파티클, 경고 UI |
| 플레이어 HP `42` | 체력바 애니메이션, 저체력 화면 효과 |
| 아이템 등급, 공격력 `35.2` | 아이템 색상, 반짝임 이펙트, 툴팁 |

조명 프리셋 ScriptableObject 같은 표현 데이터는 네트워크를 전혀 타지 않는 로컬 리소스다.

**안티패턴**: 서버가 조명 색 RGB를 매 프레임 브로드캐스트하는 것.
경과 시간 하나면 충분한데 대역폭을 낭비하고, 조명을 고칠 때마다 네트워크 코드를 건드리게 된다.

## 5. 함정 — 보이지만 판정에 걸리는 것

아래는 이펙트처럼 보이지만 **클라이언트마다 위치가 다르면 안 된다.**

- 적 공격 예고 표식 (장판, 범위 표시)
- 제한 구역 경계선
- 적 투사체
- 아이템 드랍 위치

**처리 방식**: 서버가 이벤트만 보내고(무엇을 · 언제 · 어디서) 클라이언트가 그것을 렌더링한다.
클라이언트가 스스로 위치나 타이밍을 계산하게 두면 안 된다.

```
잘못: 클라이언트가 적 애니메이션 이벤트를 보고 장판 위치를 계산
맞음: 서버가 "패턴 3, 좌표 (12, 0, 45), 1.2초 후 발동" 브로드캐스트
      → 클라이언트는 그 좌표에 장판을 그리기만
```

## 5.5 Mirror에서의 구현 매핑

이 프로젝트는 **Mirror**를 사용한다. 위 규칙을 Mirror의 API로 옮기면 아래와 같다.

### 기본 대응

| 개념 | Mirror |
|---|---|
| 네트워크 오브젝트 | `NetworkIdentity` + `NetworkBehaviour` 상속 |
| 서버 → 모든 클라이언트 상태 | `[SyncVar]`, `SyncList`, `SyncDictionary` |
| 클라이언트 → 서버 요청 | `[Command]` |
| 서버 → 모든 클라이언트 호출 | `[ClientRpc]` |
| 서버 → 특정 클라이언트 호출 | `[TargetRpc]` |
| 서버에서만 실행 | `[Server]` / `[ServerCallback]` |
| 클라이언트에서만 실행 | `[Client]` / `[ClientCallback]` |

### 현재 구현의 매핑

| 경로 | 권위와 전달 |
|---|---|
| `PlayerInputState` | 소유 클라이언트의 요청을 Command로 서버 처리기 인터페이스에 전달. session epoch·sequence·입력 서버 시각은 서버에서 검증하며 승인 순번·참가자·권위 이동·쿨다운 등은 소유자에게 동기화 |
| `PlayerCombatState` | 서버가 확정한 HP·생사·기력·공명·기술 단계·조준 상태를 동기화하며 클라이언트 hook은 표현 갱신에 사용 |
| `CompanionCombatState` | 서버 스포너가 소환 때 서버 소유로 스폰하고 복귀·재호출 때 내리는 동료 개체. 수명·체력·타깃·yaw를 SyncVar로, 위치는 `NetworkTransformReliable`로 보낸다. Command가 없다 |
| `BossState` | 서버 스포너가 보스전 시작 틱에 서버 소유로 스폰하는 보스 개체. 전투 번호·정의 ID·위치·yaw·체력·생사·흐름·페이즈를 SyncVar(10Hz)로, 예고·발동·돌진·투사체·장판 사건과 2페이즈 반월 연쇄·빔·별형 빔 사건, 50% 결계 예고·활성·완료·정리 사건을 서버 시각과 시전 번호(빔·구조·구역·결계는 서버 발급 번호)를 실은 ClientRpc로 보낸다. 진행 중인 사건(결계는 예고부터 정리 전까지)은 스폰 초기 상태에 실어 늦은 접속·재접속에 복원한다. 위치는 NetworkTransform 없이 SyncVar이고 돌진 중 몸체는 표현이 돌진 사건으로 그리는 계약이다. Command가 없다. 2026-10-12 `BossNetworkViewBinder`를 네트워크 프리팹에 연결해 몸체·예고·지속 효과·결계를 표시한다. 효과 루트는 몸체에서 분리하고 재접속 시 표현 기록을 초기화한다. 관련 EditMode 통과와 실제 M-Boss 수용은 구분한다 |
| `CombatServerRuntime`·`PlayerServer` | `Shinshi.Server`에서 이동·피해·사망·기술을 판정. 입력·피해 처리 뒤 세션 종료, 그 뒤 부활 승인·복제 |

| `ShinshiServerAuthenticator` | 인증 전 메시지로 버전·콘텐츠 해시·일회 토큰을 확인. 참가자 결합과 던전 입장 검증 뒤에만 플레이어 생성·Command 허용 |

### 후속 시스템 매핑 예시

| 시스템 | Mirror 처리 |
|---|---|
| 플레이어 HP, 스태미나 | `[SyncVar(hook = ...)]` — 훅에서 UI 갱신 |
| 게임 단계, 제한 구역 반경 | `[SyncVar]` — 클라이언트가 이 값으로 셰이더 · 미니맵 그림 |
| 경과 시간 | `[SyncVar]` 하나. 조명은 클라이언트가 계산 |
| 공용 재화 | 서버 단일 값 + `[SyncVar]`. 구매는 `[Command]` |
| 공격 · 타이밍 입력 | `[Command]` 로 전송, 서버가 판정 |
| 개인 성공 연출 | `[TargetRpc]` — 해당 플레이어에게만 |
| 적 스폰 · 사망 | 서버가 `NetworkServer.Spawn` / `Destroy` |
| 아이템 드랍 | 서버가 굴리고 `NetworkServer.Spawn` |
| 아이템 획득 | `[Command]` 요청 → 서버가 선착순 판정 |
| 적 공격 예고 | `[ClientRpc]` 로 패턴 ID · 좌표 · 발동 시각 전송 |
| 히트 이펙트, 사운드 | 동기화하지 않음. 각 클라이언트가 로컬 재생 |

### 주의할 Mirror 함정

**1. `[Command]`는 기본적으로 소유 오브젝트에서만 호출된다.**
다른 오브젝트에 대한 요청은 `[Command(requiresAuthority = false)]`를 쓰되, **서버에서 호출자 검증을 반드시 한다.** 안 하면 클라이언트가 남의 아이템을 주울 수 있다.

**2. `[SyncVar]` 훅은 클라이언트에서만 호출된다.**
데디케이티드 서버에서는 훅이 호출되지 않는다. 에디터에서 호스트 모드로 테스트하면 훅이 불리므로, 순수 서버 로직을 훅에 넣어도 로컬에서는 멀쩡해 보이다가 서버 빌드에서 깨진다.

**3. `SyncList` 변경은 요소 단위로 전송된다.**
인벤토리처럼 자주 바뀌는 것은 괜찮지만, 매 프레임 갱신되는 것을 넣으면 대역폭을 잡아먹는다.

**4. `NetworkTransform`의 역할.**
`NetworkTransformReliable`은 서버 위치 전달과 원격 플레이어 보간에 사용한다.
소유 플레이어의 입력 예측·마지막 처리 sequence·재조정이 필요하면 별도 예측 컴포넌트로 처리하며,
`NetworkTransform` 자체에 맡기지 않는다.

**보간 책임은 한 계층만 갖는다.** 원격 인스턴스는 `NetworkTransform`, 소유 클라이언트는 예측 컴포넌트다.
비서버 인스턴스의 Rigidbody는 `isKinematic = true`와 함께 `interpolation = None`으로 둔다 —
두 계층이 같은 프레임에 Transform을 밀면 떨림이 된다.

**5. 화면 표현을 Transform 위치 차분으로 역산하지 않는다.**
위치에는 서버 이동·스냅샷 보간·재조정 보정이 섞여 들어온다. 이걸 이동 방향으로 되돌리면
서버가 위치를 뒤로 보정한 순간 모델이 뒤를 본다.
방향·속도는 표현 컴포넌트가 역할별 소스(서버 동기화 값, 로컬 입력)에서 받아 보관하고, 회전은 물리 루트가 아니라
시각용 자식 피벗에만 적용한다. 루트 회전을 쓰지 않으면 `syncRotation`은 꺼 둔다.

**6. 호스트 모드는 지연이 0이다.**
개발 편의로 에디터를 호스트 모드로 띄워 혼자 테스트하면 지연 관련 결함과 서버 전용 경로의 결함을 절대 못 찾는다. 완료 판정은 서버 빌드(또는 서버 전용 실행) + 클라이언트로 한다. [멀티플레이 테스트 절차](../ai/04_MULTIPLAYER_TEST_PROTOCOL.md) 참조.

**7. `syncInterval`을 오브젝트 종류마다 다르게 잡는다.**
기본값 그대로 두면 수십 마리의 적이 플레이어와 같은 주기로 모든 연결에 전송된다.
조작 대상인 플레이어는 촘촘하게, 적처럼 보간으로 메울 수 있는 것은 성기게 잡는다. 값은 코드 계약값 상수(`Constants` partial, `Constants.network.cs`)에 모은다.

**8. 로컬 이벤트 버스는 네트워크가 아니다.**
C# `event`나 프로젝트 이벤트 버스로 서버 프로세스에서 발행한 이벤트는 원격 클라이언트에 전달되지 않는다. 지속 상태는
`SyncVar`/`SyncList`, 전체 일회성 결과는 `ClientRpc`, 개인 결과는 `TargetRpc`로 별도 전달한다.

**9. Mirror의 정적 연결 이벤트에 `+=`로 구독하면 조용히 지워진다.**

`NetworkManager`가 서버·클라이언트를 시작할 때 이 이벤트들을 **대입으로 덮어쓴다.**

```csharp
// Mirror/Core/NetworkManager.cs
NetworkServer.OnConnectedEvent    = OnServerConnectInternal;   // += 가 아니다
NetworkServer.OnDisconnectedEvent = OnServerDisconnect;
NetworkClient.OnConnectedEvent    = OnClientConnectInternal;
NetworkClient.OnDisconnectedEvent = OnClientDisconnectInternal;
```

밖에서 `+=`로 걸어 둔 구독은 `StartHost`/`StartClient`가 불리는 순간 통째로 사라진다.
**예외도 경고도 없다.** 이벤트가 한 번도 오지 않는 것으로만 드러나므로 원인을 찾기 어렵다.
연결 이후 단계 전환 로그가 빠져 있으면 이 함정부터 의심한다.

**대신 `NetworkManager`를 상속해 콜백을 오버라이드하고, 거기서 프로젝트 이벤트를 다시 낸다.**

```csharp
public override void OnClientConnect()
{
    base.OnClientConnect();
    ClientConnected?.Invoke();
}
```

현재 [ShinshiNetworkManager](../../Assets/01.Scripts/01.Network/ShinshiNetworkManager.cs)는 `OnServerDisconnect`를 오버라이드하고 서버 개체 유지·기본 연결 정리 뒤 `ServerDisconnected`를 낸다. `ServerBootstrap`이 서버 인증기의 정리를 이 이벤트에 연결한다. 클라이언트 인증 거절·같은 토큰 재시도는 `ShinshiClientAuthenticator.Rejected`·`JoinRetryScheduled`를 구독한다. 위 코드의 `ClientConnected`·`ClientDisconnected`는 설명용 이름이며 현재 매니저가 제공하는 멤버가 아니다. 새 클라이언트 연결 이벤트가 필요하면 같은 콜백 재발행 방식으로 계약을 추가한다.

### 트랜스포트

트랜스포트는 Mirror 기본 KCP(UDP)로 시작한다. 호스팅은 로컬 개발에서 시작해 AWS로 옮긴다(확정, 2026-09-30). 서버 구성과 이전 단계는 [7장](#7-데디케이티드-서버-운영-원칙)에 적는다. 클라우드에서는 보안 그룹 등에서 KCP 포트를 **UDP**로 열어야 한다.
**연결 경로가 달라도 게임 판정 권위는 데디케이티드 서버에 남는다.** 트랜스포트나 외부 서비스(로그인, 매칭 등)를 붙이더라도 게임 시뮬레이션의 판정을 그쪽으로 옮기지 않는다.

체험판에는 KCP 암호화를 적용하지 않는다(2026-10-01 결정). API의 HTTPS·Bearer 인증은 별도의 HTTP 경로에 적용되며 게임 UDP 트래픽 암호화의 근거로 삼지 않는다.

## 6. 타이밍 판정 — 지연이 가장 크게 드러나는 곳

판정 창이 짧은 입력(예: 회피, 반격)은 네트워크 지연이 50~150ms만 생겨도 서버의 판정 결과와 클라이언트의 체감이 어긋난다. 이런 기능이 기획에 들어오면 아래 방향을 따른다.

### 입력 계약과 현재 범위

현재 `PlayerInputHeader`는 session epoch·sequence·추정 서버 시각을 담고 `PlayerInputGate`가 결합된 참가자·순서·허용 시각을 검증한다. 시각 허용 창은 [Constants.network.cs](../../Assets/01.Scripts/00.Common/Constants/Constants.network.cs)의 과거 150ms·미래 50ms다. 서버 틱은 30Hz, 플레이어 위치 복제는 초기 15Hz, 적·마을 원격은 10Hz이며 수용량·체감 측정 뒤 조정한다. 아래 판정 창 ID·소비 계약은 타이밍 창을 추가할 때의 요구사항이며 현재 모든 타이밍 기술이 구현됐다는 뜻은 아니다.

입력 주기 상한(초당 30건, `INPUT_SEND_RATE_MAX`)을 넘긴 입력은 버린다. 토큰 버킷은 초당30건 보충·버스트10이며, 초과가 발생한 서버 시각을 `Math.Floor`로 나눈 서로 다른 1초 구간이 10초 창 안에서5개가 되면 연결을 끊는다. 각 구간의 마지막 초과 시각으로 만료하며 정확히10초 지난 구간은 제외한다. 순번 역행·유효하지 않은 입력 시각의30회 차단은 별도 계수다. 재접속에는 위반 구간과 토큰 잔량·마지막 보충 시각을 함께 보존한다. 참가자ID·계수를 기록한다. 2026-10-11 규칙과 회귀시험을 반영했으며 실제 M3 지연·폭주 수용과 런타임 할당 실측은 미검증이다.

### 판정 창을 추가할 때

1. 서버가 판정 창별 ID, 대상, 시작·종료 서버 시각, 소비 여부를 보유
2. 클라이언트가 요청 ID, 판정 창 ID, 입력 순서와 추정 서버 시각을 함께 전송
3. 서버가 시각을 허용 범위(뒤·앞 한계)로 제한하고 현재 상태·생명·쿨다운·자원·판정 창의 대상/소비 여부를 검증한 뒤 판정
4. 성공하면 판정 창을 먼저 소비하고 권위 결과를 한 번만 커밋
5. 클라이언트는 입력 **모션을 즉시 재생**하되, 성공 연출은 서버 응답 후 확정한다.
   판정 불일치 시 롤백 대신 서버 결과를 우선한다

### 검증 시 확인할 것

- 지연 0ms(로컬), 50ms, 150ms 조건에서 각각 성공률을 비교한다
- 손실 1%·3% 조건에서도 중복·순서·누락과 체감을 확인한다(2026-10-01 결정)
- 클라이언트가 "맞았다고 느꼈는데 실패"하는 빈도를 기록한다
- 데디케이티드 서버에서는 모든 플레이어가 지연을 겪는다. 호스트 모드에서 잰 성공률은 판정 근거로 쓰지 않는다

데디케이티드 서버라 특정 플레이어만 지연 0으로 유리해지는 구조는 없다. 대신 모든 플레이어의 체감이 지연에 좌우되므로, 체감 차이가 크면 판정 창을 늘리는 쪽으로 대응한다.

## 7. 데디케이티드 서버 운영 원칙

호스트 방식은 데디케이티드 서버(확정)다. 게임 판정은 플레이어가 없는 서버 프로세스가 맡고, 모든 플레이어는 클라이언트로 접속한다.

**규칙**: 판정 로직이 "서버에 로컬 플레이어가 있다"고 가정하지 않는다.

```
잘못: if (isServer && isClient) { /* 호스트 전용 판정 로직 300줄 */ }
잘못: 서버 판정 중에 NetworkClient.localPlayer, Camera.main, UI를 참조
맞음: 판정 로직을 [Server] 메서드로 분리하고, 서버에 화면·입력·로컬 플레이어가 없어도 동작하게 한다
```

- Runtime 상태 변경은 `[Server]` 경로로만 하고 판정 객체는 `Shinshi.Server`에서 실행한다
- `isLocalPlayer` 분기는 입력 · UI · 카메라에만
- 서버 빌드는 화면 없이(헤드리스) 돈다. 카메라 · 오디오 · UI · VFX 같은 표현 컴포넌트는 서버에서 동작하지 않아도 판정이 깨지지 않게 둔다. 판정이 표현 컴포넌트의 값(애니메이션 이벤트, 파티클 수명 등)에 기대지 않는다
- 에디터 호스트 모드는 개발 편의용이다. 호스트 모드에서만 확인한 기능은 완료로 보고하지 않는다 ([멀티플레이 테스트 절차](../ai/04_MULTIPLAYER_TEST_PROTOCOL.md))
- 서버 실행 설정·인증·존재 신호·출정 종료 경로는 구현돼 있다. 2026-10-11 Windows IL2CPP·Linux Mono 개발 빌드와 격리 Linux 서버 기동·협조 종료는 확인했다. 실제 다인 접속·배포·systemd 연동과 운영 텔레메트리 수용은 별도 확인이 필요하다

### 7.1 서버 구성 (확정, 2026-09-30)

신시는 여러 파티가 함께 보이는 MMORPG식 공유 마을이고, 전투는 파티(1~4인) 단위 던전에서 한다. 목표 동시 접속은 당장 10~100명이며 이후 늘릴 수 있다. 모든 판정은 데디케이티드 서버가 맡는다(플레이어 호스트 없음).

| 계층 | 역할 | 구현 | 100명 기준 규모 |
|---|---|---|---|
| 마을 서버 (신시) | 공유 공간, 부적 교체, 파티 모집 | Unity C# + Mirror 역할 부트스트랩·입장 인증 구현. 공간 기반 Interest Management와 마을 기능 통합은 목표 | 프로세스 1개 |
| 던전 서버 | 파티 하나의 웨이브·보스전 판정 | Unity C# + Mirror, 풀 존재·출정 명단·전투·저장·정산 구현. 일반전 웨이브·스폰과 보스 마지막 단계 연결은 남음 | 파티당 1개. 100명이 모두 4인 출정하면 25개, 모두 솔로면 100개 필요. 실제 풀 상한은 실측하고 부족하면 대기열 적용 |
| 백엔드 API | 로그인·접속 토큰, 예약·배정·시작·이벤트 저장·정산·장애 복구 | [ASP.NET Core API](../../Backend/src/Shinshi.Api/Program.cs) 구현. 캐릭터·인벤토리 등 전체 도메인 API 완료를 뜻하지 않음 | 초기 1개 |
| DB | 영구 데이터 | PostgreSQL, [Npgsql+Dapper 데이터 계층](../../Backend/src/Shinshi.Data/Shinshi.Data.csproj)과 [SQL migration](../../Backend/src/Shinshi.Data/SqlMigrationRunner.cs) 구현 | 초기 1개 |

- 게임 서버(마을·던전)는 클라이언트와 같은 Unity 프로젝트·같은 코드에서 빌드한다. 서버 역할은 빌드를 나누지 않고 실행 인자로 고른다
- 던전은 프로세스 하나에 **출정 하나**를 돌린 뒤 종료한다. `ServerShutdownController`가 드레인·연결 정리·flush를 수행하고 [systemd 던전 유닛](../../deploy/gameserver/shinshi-dungeon@.service)의 `Restart=always`가 새 프로세스를 띄운다. `ServerPresence`는 매번 새 bootId로 등록한다. 같은 프로세스의 명단·닫힘 기록·보존소를 다음 출정에 재사용하지 않는다. 프로세스당 메모리는 서버 빌드로 실측한 뒤 적는다
- 마을에서 던전으로 갈 때는 백엔드가 던전 서버 주소와 60초 일회용 토큰을 내주고, 던전 서버가 API 교환·서버 역할·인스턴스·출정·참가자 결합을 확인한 뒤 받는다. 입장 후 계정 접속 임대 이관과 start 영수증이 확정돼야 전투를 시작한다. 이벤트·정산은 던전 서버가 백엔드에 보고한다
- **DB에 쓰는 것은 백엔드뿐이다.** 게임 서버도 백엔드 API를 거친다. 클라이언트는 어떤 저장 경로에도 직접 쓰지 않는다
- 백엔드는 게임 판정을 하지 않는다. 판정 권위는 마을·던전 서버에 있다
- 서버 주소·포트·백엔드 URL·서버 역할은 코드에 박지 않고 **명령줄 인자나 환경변수**로 받는다
- 이 규모에서는 Redis, 마을 채널 분할, 관리형 게임 서버 호스팅(GameLift 등)을 쓰지 않는다. 대신 백엔드가 마을 서버 목록을 내려주는 구조로 두어 채널을 나중에 늘릴 수 있게 한다

### 7.1.1 인증·경제 경계

- 접속 프로토콜은 `Constants.Network.PROTOCOL_VERSION`(현재 6)을 따르며 닉네임·외형·경험치는 API 토큰 교환 때 소유 캐릭터의 DB 값으로 읽고, 서버가 검증해 최초 생성·재결합 전에 적용한다. 경험치 누계와 마지막 사건 순번은 같은 캐릭터 행에서 읽고 예약 장비 스냅샷과 분리한다. 외형 payload 버전과 기존 캐릭터 해석은 [캐릭터 커스터마이즈](CHARACTER_CUSTOMIZATION.md)를 따른다.

- HTTP 토큰은 `Authorization: Bearer {token}`으로 보낸다. 게임 서버의 서비스 자격은 임대 발급에만 쓰고, 이후 서버 경로는 `ServerCredentials`의 유효한 서버 임대 토큰을 사용한다. 인스턴스 헤더만으로 서버를 인증하지 않는다. 실행 설정은 [ServerLaunchConfig](../../Assets/01.Scripts/98.Servers/01.Network/Bootstrap/ServerLaunchConfig.cs)·[BackendLaunchSettings](../../Assets/01.Scripts/98.Servers/01.Network/Backend/BackendLaunchSettings.cs)가 기준이다.
- 서비스 자격은 `BACKEND_SERVICE_TOKEN` 또는 `-backend-service-token-file`의 파일로 공급한다. 토큰 원문을 CLI 인자·SO·로그에 넣지 않는다. 출시 서버는 API 검증기를 쓰고, `dev` 검증기는 에디터·개발 빌드 전용이며 형식만 확인한다. 출시 서버는 서비스 자격 없이 던전을 열지 않는다.
- 동시 접속은 거절하며 사용자 문구는 **“이미 접속 중인 계정”**, 코드 `AlreadyConnected(809)`다. 늦은 끊김 감지를 기다리는 같은 토큰 재시도와 실제 던전 재입장 토큰 발급을 구분한다. 진행 중 재접속 유예에서는 원래 서버 개체가 피격·사망·타이머를 계속 받고, 복귀 시 같은 참가자에게 재결합한다. 자세한 흐름은 [협업 문서 9장](SERVER_CLIENT_WORKFLOW.md#9-인증재접속서버-수명-연결)을 따른다.
- 백엔드 일시 불가 `BackendUnavailable(810)`와 호출 제한 `RateLimited(811)`을 토큰 변조 사유와 구분한다. 정산 상한 초과는 `SettlementLimitExceeded(904)`다. 값의 원본은 [ERejectReason](../../Assets/01.Scripts/00.Common/Types/ERejectReason.cs)과 [ContractCodes](../../Assets/01.Scripts/00.Common/Contracts/ContractCodes.cs)다.
- 서버는 [SettlementGrant](../../Assets/01.Scripts/00.Common/Contracts/Sessions/SettlementGrant.cs)의 지갑 자산 칸(정기·정련편·티켓·엽전), 아이템 칸과 부적 칸을 구분해 정산안을 보낸다. 정산 아이템은 계정 귀속이다. 지갑 자산을 일반 아이템 ID로 지급하지 않는다. API는 정산안의 상한·자격·멱등성·원장과 트랜잭션을 확인하고 게임 처치를 다시 시뮬레이션하지 않는다.
- 서비스 장애 취소의 현행 정책은 완료 웨이브 기본 정기와 서버 원장으로 확인된 미정산 추가 정기를 모두 100% 지급하는 것이다(2026-10-08 사용자 결정, 기존 추가 50% 정책 대체). 현재 `SettlementRules`의 `ServiceCancelled`와 API 장애 취소 정산은 100%이고 `Assets/09.Data/Session/SessionConfig.asset`의 정책은 2(`FullGrant`)다. 회귀 테스트는 실제 PostgreSQL 18 격리 컨테이너에서 통과했고(2026-10-10 실제 검증, 134/134) 실제 서버 소실 실행(M2/M3)은 아직 검증하지 않았다. 일반 실패·포기의 추가 정기 50% 보존은 유지한다. 운영자 `ForceClose`는 장애 취소와 분리되어 추가 정기 50% 내림을 현행 유지하며 지급률은 기획 미정이다. 상세는 [기술 설계](../03-technical-design.md)와 [로드맵](../05-implementation-roadmap.md)을 따른다.
- 운영 제어는 관리자 API·CLI로 한다(2026-10-01 결정). 게임 클라이언트에 관리자 경제 쓰기 경로를 두지 않는다. DTO 원본은 [Contracts](../../Assets/01.Scripts/00.Common/Contracts/ApiRoutes.cs)이며 [백엔드 Contracts csproj](../../Backend/src/Shinshi.Contracts/Shinshi.Contracts.csproj)가 소스를 링크한다.

### 7.2 호스팅 단계 (확정, 2026-09-30)

| 단계 | 구성 |
|---|---|
| 1. 로컬 개발 | 에디터 또는 헤드리스 빌드로 게임 서버 실행, 백엔드는 로컬 실행, DB는 [Docker Compose](../../Backend/docker-compose.yml). 구성 파일·M2 실행 도구와 개발 빌드 근거는 있으며 M2/M3 통합은 미검증 |
| 2. AWS 초기 | 게임 서버와 백엔드를 EC2(Linux) 한두 대에, DB는 RDS |
| 3. AWS 확장 | 필요해지면 던전 서버를 자동 확장 풀이나 관리형 호스팅으로, 백엔드를 컨테이너로 옮긴다. 이때 채널 분할과 Redis를 검토한다 |

서버 빌드는 처음부터 Linux 헤드리스로 뽑아 확인한다. 인스턴스 사양은 헤드리스 프로세스 메모리와 100명 부하 테스트 결과로 정한다.

이번 동기화는 실제 소스·asmdef·DTO·배포 템플릿과 문서의 정적 대조다. 기존 실행 근거로 제공된 것은 사용자 제공 Unity Test Runner EditMode 780개 통과와 Backend 396개 통과(PostgreSQL 18 Docker)뿐이다. 이를 서버 빌드·M2/M3·IL2CPP·Linux/systemd 배포 검증으로 확장하지 않는다. `ServerShutdownController`의 애플리케이션 종료와 systemd의 재시작 설정은 구현돼 있지만 OS `SIGTERM`을 자동으로 드레인에 연결하는 코드는 확인되지 않았다.

## 9. 판단이 애매할 때

표에 없는 항목이면 아래 순서로 판정한다.

1. 이 값이 다르면 누군가 죽거나, 아이템을 얻거나, 점수가 달라지는가? → 서버
2. 이 값이 다르면 화면만 조금 달라 보이는가? → 클라이언트
3. 그래도 애매하면 **서버로 두고 팀에 물어본다.** 나중에 클라이언트로 내리는 것이, 클라이언트에 뒀다가 서버로 올리는 것보다 훨씬 싸다.

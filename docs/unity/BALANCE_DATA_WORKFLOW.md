# 밸런스 데이터 작업

> 2026-09-30 shinshi 기준으로 이식.
> 처음 넣는 수치는 모두 프로토타입용 시작점이다. 플레이 테스트를 거치며 상당수가 바뀐다.
> 그때마다 코드를 고치고 빌드하면 팀 전체가 기다린다.

GameDB 루트와 `PlayerConfigSO`, `SessionConfigSO`는 구현되어 있다(`Assets/09.Data/`). 나머지 `*SO`는 첫 밸런스 수치를 넣는 사람이 이 문서와 [코딩 컨벤션](../coding-convention.md) 16장(데이터 관리)의 규칙대로 추가한다. 루트 DB, 초기화 순서, 폴더 배치(`Assets/09.Data/`)는 코딩 컨벤션 16장이 기준이고, 이 문서는 값을 바꾸고 기록하는 작업 절차를 다룬다.

---

## 1. 원칙

**밸런스 수치를 코드 상수로 박지 않는다.**

```csharp
// 잘못
private const float DodgeCooldown = 0.8f;

// 맞음 - GameDB의 ScriptableObject 값을 읽는다 (읽는 시점은 코딩 컨벤션 16장)
private PlayerConfigSO _playerConfig;

private void Start()
{
    _playerConfig = GameDB.Player;
}
// _playerConfig.DodgeCooldown 을 참조
```

어떤 값이 밸런스 수치(GameDB)이고 어떤 값이 코드 계약값(Constants)인지의 구분은 [코딩 컨벤션](../coding-convention.md) 16장을 따른다.

---

## 2. ScriptableObject 대상

데이터 종류마다 `*SO` 클래스를 하나씩 두고, 소유 파트를 정한다. 게임 수치의 설계 기준은 [기획서](../02-game-design.md)와 연결 부록, 구체적 SO 대상과 모듈 배치는 [아키텍처](../04-architecture.md)를 따른다. 구현된 클래스는 `PlayerConfigSO`, `SessionConfigSO` 둘이고, 아래 표는 새 항목을 추가할 때 쓰는 형식 예시다.

| 데이터 | 담는 것 | 소유 파트 |
|---|---|---|
| `{도메인}ConfigSO` | {수치 목록} | {파트} |

한 SO는 한 파트가 소유한다. 소유 파트가 4장의 "승인 없이 가능" 범위를 정한다.

---

## 3. 설계도와 인스턴스 분리

아이템처럼 개별 생성마다 값이 다른 것은 두 층으로 나눈다.

| 구분 | 역할 | 형태 |
|---|---|---|
| `{아이템}SO` | 원본 설계도. 등급, 이름, 수치 범위 | ScriptableObject |
| `{아이템}Snapshot` | 개별 생성 결과. 실제 굴려진 수치 | 직렬화 값 타입 |

이렇게 해야 같은 아이템이라도 생성마다 수치가 달라지는 구조가 깔끔하다.
나중에 수치 재조정이나 등급 상승 같은 기능이 생겨도 이 구조를 그대로 재사용한다.

런타임에 SO 에셋 자체의 값을 바꾸지 않는다. 에디터에서는 Play Mode에서 바꾼 SO 값이 에셋에 그대로 남는다. 바뀌는 값은 인스턴스 층에 둔다.

---

## 4. 값을 바꿀 때

### 승인 없이 가능

- 자기 파트 소유 ScriptableObject의 값 조정
- 프로토타입 기간 중

### 팀에 알려야 함

- 다른 파트 소유 데이터의 값
- 여러 시스템에 연쇄 영향을 주는 값 (예: 플레이어 HP → 적 공격력 전부 재조정 필요)
- 스코프에 영향을 주는 구조 변경 (필드 추가 · 삭제)

### 사전 승인 필요

- ScriptableObject의 **필드 구조 변경**. 기존 에셋의 값이 초기화될 수 있다

---

## 5. 필드 구조를 바꿀 때

ScriptableObject에 필드를 추가하거나 이름을 바꾸면 기존 에셋의 값이 날아갈 수 있다.

| 변경 | 안전한가 |
|---|---|
| 필드 추가 | 안전. 기본값으로 채워짐 |
| 필드 삭제 | 값 소실. 기록해두고 진행 |
| 필드 이름 변경 | **값 소실.** `[FormerlySerializedAs("옛이름")]`를 붙인다 |
| 타입 변경 | 값 소실. 되도록 피한다 |
| enum 값 재배열 | **직렬화된 값이 어긋난다.** 명시값을 유지하고 기존 값을 재배열하지 않는다 |

```csharp
using UnityEngine.Serialization;

[FormerlySerializedAs("dodgeTime")]
[SerializeField] private float _dodgeCooldown;
```

## 6. 검증

L1, L2 등 검증 수준은 [검증 플레이북](../ai/03_VERIFICATION_PLAYBOOK.md)을 따른다.

| 변경 | 최소 검증 |
|---|---|
| 값만 조정 | L1 + 해당 값이 실제로 반영되는지 1회 확인 |
| 필드 추가 | L1 + 기존 에셋의 다른 값이 유지됐는지 확인 |
| 필드 이름 · 타입 변경 | L1 + **모든 관련 에셋을 열어 값 확인** |
| 연쇄 영향 있는 값 | L2 + 영향받는 시스템 회귀 확인 |

값을 바꾼 뒤 **인스펙터에서 실제로 반영됐는지 눈으로 확인한다.** 코드만 보고 넘어가지 않는다.

---

## 7. 문서와의 동기화

[기획서](../02-game-design.md)의 수치와 실제 ScriptableObject 값은 플레이테스트 조정 과정에서 달라질 수 있다. 아직 SO가 없는 항목은 기획서와 연결 부록의 초기값을 구현 출발점으로 삼는다.

- 코드와 데이터가 최신
- 문서는 설계 의도와 근거를 담는다
- 큰 변경이 있으면 문서도 갱신하되, 매번 동기화하려 애쓰지 않는다

**충돌 시 데이터를 우선하고, 차이가 크면 보고한다.**

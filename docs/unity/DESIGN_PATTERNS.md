# 디자인 패턴 지도

2026-09-30 shinshi 기준으로 이식. shinshi에는 아직 게임 코드가 없다. 이 문서는 **채택할 패턴과 선택 규칙**을 먼저 정해 두고, 코드가 생기면 실제로 적용된 자리를 채워 가는 지도다.

> 이 문서의 목적은 두 가지다.
> 1. **선택 규칙을 먼저 남긴다.** 경계를 넘어 알리는 방법은 여럿인데, 어느 것을 언제 쓰는지 정해 두지 않으면 팀원이 각자 즉흥으로 고르고 그 지점부터 갈라진다.
> 2. **있는 것을 보이게 한다.** 패턴을 코드에 넣으면 이 문서 2장 표의 "적용 위치" 칸에 적는다. 코드를 처음 읽는 사람은 적혀 있지 않은 패턴을 못 본다.

예시의 클래스와 이벤트 이름은 모두 설명용이다. 실제 이름은 코드를 만들 때 정하고 [코딩 컨벤션](../coding-convention.md)을 따른다.

---

## 0. 대원칙 - 패턴이 먼저가 아니다

이 프로젝트에서 패턴을 넣는 근거는 **셋 중 하나여야 한다.**

| 근거 | 예 |
|---|---|
| **지금 있는 중복을 없앤다** | 세 파일이 같은 5단계를 각자 다시 쓰고 있다 |
| **되돌리면 깨지는 순서를 고정한다** | 자원 차감이 게이트보다 먼저 오면 거부된 요청이 스태미나를 먹는다 |
| **아직 없는 파트를 기다리지 않게 한다** | 적 AI 구현 전에도 피격 연출을 만들 수 있다 |

**"패턴을 쓰고 싶어서"는 근거가 아니다.** 아래 표의 "왜" 칸을 코드로 답할 수 없으면 그 패턴은 빼는 것이 맞다.

## 1. 경계를 넘어 알리는 방법 - 선택 규칙

기전마다 맞는 자리가 다르다. 새 알림을 만들 때 위에서부터 맞는 행을 고른다.

| 무엇을 알리나 | 기전 | 왜 |
|---|---|---|
| **내 캐릭터의 이산 전이** | **C# event** | 생사 전환, 무기 교체, 목표 지정·해제처럼 드물게 바뀌는 것. 드물게 갈리므로 이벤트가 싸다 |
| **내 캐릭터의 연속값** | **프로퍼티 폴링** | 게이지, 남은 시간, 진행도. **매 서버 틱 바뀌는 값에 이벤트를 달면 초당 수십 번 호출이 나가는데 UI가 하는 일은 같다** |
| **주인 없는 세계의 사실** | **이벤트 버스** (`GameEventBus`, 도입 예정) | 경기 단계 전환, 적 사망, 목표 달성 |
| **구현이 통째로 갈릴 수 있는 협력자** | **정적 로케이터** | 연출 구현, 아직 없는 파트의 판정. 없을 때는 Null Object가 받는다 |
| **갈아 끼울 것이 없는 순수한 값** | **정적 값 채널** | 카메라 각도처럼 그냥 숫자인 것. 로케이터를 또 만들 이유가 없다 |

### 1.1 버스에 "내 값"을 싣지 않는 이유

이벤트 버스는 방향이 없다. 씬 로컬 싱글턴으로 만들면 서버와 클라이언트 양쪽에 하나씩 떠 있고 `Publish`를 아무나 부를 수 있다.

HP 같은 자기 캐릭터 값을 버스에 실으면 **누구의 값인지 페이로드에 넣어야 하고 받는 쪽이 다시 걸러야 한다.** 여러 명이 접속하면 내 HP 바가 남의 HP 변화를 매번 받아서 버린다. 로컬 플레이어 참조가 할 일을 더 비싸게 다시 하는 것이다.

**버스는 주인이 없는 사실에만 쓴다.** 이벤트 종류를 늘리는 것 자체가 목표가 아니다.

버스는 네트워크가 아니다. 버스 이벤트는 같은 프로세스 안에서만 퍼진다. 다른 기기에 알려야 하면 [네트워크 권위](NETWORK_AUTHORITY.md)의 규칙을 따른다.

## 2. 채택할 패턴

"적용 위치" 칸은 지금 비어 있다. 패턴을 코드에 넣은 사람이 클래스 이름을 적는다.

### 2.1 생성

| 패턴 | 언제 쓰나 | 왜 | 적용 위치 |
|---|---|---|---|
| **싱글턴** | 씬을 넘겨 사는 관리자, 씬 안에서만 사는 관리자 | 두 종류를 **타입으로 가른다.** 어느 쪽인지 상속만 보면 안다. 규칙은 [코딩 컨벤션](../coding-convention.md) 싱글턴 장 | (미정) |
| **팩토리 메서드** | 종류가 서버에서 정해진 뒤 구체 객체를 만들 때 (예: 적 종류별 행동 로직) | 호출부가 구체 타입을 몰라야 종류가 늘어도 호출부를 안 고친다 | (미정) |
| **빌더** | 데이터 에셋 하나에서 복잡한 구조를 조립할 때 (예: 경기 진행표) | 검증을 조립 시점에 한 번만 한다 | (미정) |
| **오브젝트 풀** | 로컬 연출 전용 | 짧게 반복 생성되는 VFX의 할당을 없앤다. [Unity 엔지니어링 패턴](UNITY_ENGINEERING_PATTERNS.md) 6장 | (미정) |

### 2.2 구조

| 패턴 | 언제 쓰나 | 왜 | 적용 위치 |
|---|---|---|---|
| **서비스 로케이터** | 한 파트가 다른 파트의 구현을 호출해야 하는데 그 파트가 아직 없거나 구현이 갈릴 때 | 호출하는 쪽이 구현 클래스를 참조하지 않는다. **아직 없는 파트를 기다리지 않고 착수할 수 있다** | (미정) |
| **널 오브젝트** | 로케이터의 폴백 | 등록이 없으면 아무것도 안 하는 구현을 돌려주므로 **호출부에 null 체크가 없다** | (미정) |
| **퍼사드 / 메디에이터** | UI가 로컬 플레이어의 여러 컴포넌트를 읽어야 할 때 | UI가 컴포넌트 여럿을 각자 잡는 대신 창구 하나만 안다 -> 아래 2.5 | (미정) |
| **값 채널** | 오브젝트가 아니라 값만 오갈 때 | 아래 2.6 | (미정) |

### 2.3 행위

| 패턴 | 언제 쓰나 | 왜 | 적용 위치 |
|---|---|---|---|
| **옵저버** | 위 1장 | C# event와 이벤트 버스 | (미정) |
| **전략** | 종류마다 결정만 다르고 실행은 같을 때 (예: 적 종류별 행동 결정) | 이동, 공격 실행은 공용 컨트롤러가 맡고 결정만 갈아 끼운다 | (미정) |
| **템플릿 메서드** | 순서는 고정이고 단계 내용만 다를 때 | 순서는 베이스가 고정하고 각 구현이 빈칸만 채운다 | (미정) |
| **커맨드** | 클라이언트 요청을 서버가 받아 처리하는 단발 행동 | 아래 2.4 | (미정) |
| **상태** | 상태가 많고 전이 조건이 복잡할 때 | **상태가 몇 개 안 되고 단순하면 `enum` 스위치로 둔다.** 복잡도가 기준이다 | (미정) |

### 2.4 커맨드 + 템플릿 메서드 - 단발 행동

```
TryAccept(requestId) -> 게이트 -> 자원 차감 -> 커밋 -> 거부 사유 반환
```

공격, 회피처럼 클라이언트가 요청하고 서버가 받아들이는 단발 행동이 **둘 이상 같은 순서를 반복하게 되면** 이 뼈대로 묶는다. 파이프라인 하나가 순서를 소유하고, 각 행동 구현이 빈칸을 채운다.

- **순서를 손으로 다시 쓰면 한 단계를 빼먹어도 컴파일이 된다.** 뼈대로 묶는 근거는 그 중복이다.
- **변경 가능한 struct를 `readonly` 필드로 두지 않는다.** 메서드를 부를 때마다 방어 복사본이 생겨 상태 변경이 사라진다. 요청 중복 차단 같은 추적기가 조용히 동작하지 않게 된다.
- **요청마다 커맨드 객체를 새로 만들지 않는다.** 요청은 구조체로 받고, 파이프라인은 `98.Servers/`의 서버 처리기가 한 번 만들어 재사용한다([코딩 컨벤션](../coding-convention.md) 9장). 초당 여러 번 도는 경로에서 매 입력 GC 할당을 만들면 안 된다.
- **거부 사유를 돌려준다.** 거부되면 조용히 `return`하는 코드는 사람도 로그도 "입력이 씹혔다"와 "거부됐다"를 구분할 수 없다.
- **이미 검증을 통과한 행동을 뼈대에 맞추려고 뜯지 않는다.** 뼈대에 없는 단계가 필요한 행동은 밖에 둔다. 손대면 그 검증이 통째로 무효가 된다.

> **패턴 이름을 하나로 우기지 않는다.** 요청 구조체는 커맨드고, 실행 순서는 템플릿 메서드다. 둘 다 맞다.

### 2.5 퍼사드 / 메디에이터 - UI가 로컬 플레이어를 읽는 창구

UI가 로컬 플레이어 상태를 읽는 창구를 하나로 둔다. **값을 전달만 하는 자리가 아니라 셋을 한 군데서 푼다.**

1. **자기 캐릭터를 언제 잡을 수 있는지.** UI는 스폰보다 먼저 켜져 있을 수 있어, 창구가 없으면 패널마다 null 분기를 다시 쓰게 된다
2. **늦게 구독한 화면에 현재 값을 흘려 주는 것.** 이것이 없으면 나중에 열린 패널은 현재 상태를 모른 채 시작한다
3. **사망, 재접속으로 인스턴스가 갈릴 때 구독을 옮기는 것.** 패널마다 하면 언젠가 하나가 파괴된 컴포넌트를 붙들고 있는다

### 2.6 값 채널

로케이터를 또 만들지 않는 자리다. 카메라 각도처럼 갈아 끼울 구현체가 아니라 그냥 숫자인 것에 쓴다.

```
카메라 yaw   카메라 파트 -> 공용(Shinshi.Common) -> 이동 파트
목표 지정    전투 파트   -> 공용(Shinshi.Common) -> 카메라 파트
가림 투명화  카메라 파트 -> 공용(OcclusionFadeChannel) -> 전투 입력(커서 판정)
```

**방향이 반대여도 어느 쪽도 상대 어셈블리를 참조하지 않는다.** 값을 쓰는 쪽이 없는 씬에서는 기본값(예: yaw 0)으로 동작하고, 붙이면 저절로 살아난다.

## 3. 일부러 하지 않을 것

**안 한 이유가 적혀 있지 않으면 다음 사람이 "빠뜨린 것"으로 보고 넣는다.** 코드가 생겨 새로 하지 않기로 한 것이 있으면 이 표에 이유와 함께 더한다.

| 무엇 | 왜 안 하나 |
|---|---|
| **네트워크 개체를 로컬 오브젝트 풀에 넣기** | `NetworkServer.Spawn`으로 뜨는 개체는 로컬 풀 대상이 아니다. 네트워크 개체 풀링은 Mirror의 스폰 핸들러를 등록하는 **별개의 작업**이다 |
| **파라미터만 다른 변형을 각각 클래스로 빼기** | 축이 파라미터로 고정되면 클래스 N개가 서로 복붙이 된다. 템플릿 몇 종 x 파라미터로 둔다 |
| **단순한 상태를 클래스로 빼기** | 상태 몇 개가 단순하면 `enum` 스위치로 읽힌다. **복잡도가 기준이지 일관성이 기준이 아니다** |
| **데이터 중심 시스템(장비, 상점 등)에 미리 패턴 잡기** | 이런 시스템의 패턴은 이미 골라져 있다 - GameDB ScriptableObject ([밸런스 데이터 작업](BALANCE_DATA_WORKFLOW.md)). **더 얹는 것이 과설계다** |
| **이벤트 버스 이벤트 늘리기** | 위 1.1 |
| **검증된 행동을 커맨드 뼈대에 억지로 넣기** | 위 2.4 |
| **게임 카메라 방위 회전** | 클릭 이동과 커서 조준이 월드 지점을 쓰므로 회전 없이 조작이 성립한다. 넣으면 카메라 방위를 이동 쪽에 넘기는 값 채널과 화면 기준 예고 확인이 함께 필요하다. 줌 단계마다 내려다보는 각은 바뀌지만 방위는 고정이다 (2026-10-02 사용자 결정: 휠 3단계 줌) |

## 4. 이후 확장 자리

| 패턴 | 어디에 | 언제 |
|---|---|---|
| **상태** | 전이가 복잡한 AI나 경기 흐름 | 상태와 전이 조건이 `enum` 스위치로 읽히지 않을 만큼 늘었을 때 |
| **데코레이터 또는 책임 연쇄** | 피해, 스탯 수정자 | **수정자 종류와 수치가 기획으로 정해진 뒤.** 지금 깔면 요구가 안 맞을 때 체인을 통째로 뒤집게 된다 |

## 5. 이 문서를 갱신할 때

- 표의 패턴 이름보다 실제 책임 경계와 호출 방향을 우선한다.
- 패턴을 코드에 넣으면 2장 "적용 위치" 칸을 채운다. 이름만 있는 빈 타입은 적지 않는다.
- 선택 규칙(1장)과 다르게 구현해야 하면 먼저 팀에 알리고 이 문서를 고친다.

# 모호한 요청 명확화

## 언제 발동하나

다음 중 하나라도 해당하면, 코드를 바로 수정하거나 구현하기 전에 이 스킬을 따른다.

- 지시어만 있고 대상이 없음: "이거 고쳐줘", "더 낫게 해줘", "정리해줘"
- 대상은 있으나 범위가 불명확: 어떤 씬, 폴더, 스크립트인지, 얼마나 넓게 손댈지 불특정
- 구현 방식이 여러 갈래로 갈리고 각각 결과물이 달라짐 (예: 저장 위치, 네이밍, UI 방식, 네트워크 동기화 여부)
- 요청이 아직 정해지지 않은 값에 기댐: 게임 장르와 시스템(기획서 없음), 서버 빌드 설정·인증 방식(미정. 데디케이티드 서버, 마을·던전·백엔드 구성, 로컬에서 AWS 이전은 확정), 최대 인원(`{최대 인원}`), 파트와 담당자(`{파트}`, `{팀원이름}`)
- 이 변경이 다른 코드, 문서, 팀원 작업에 영향을 줄 수 있는데 그 영향 범위가 불확실

[응답 스타일](../../../docs/ai/10_RESPONSE_STYLE_GUIDE.md)의 "사실 · 추정 · 미검증을 구분한다", [에이전트 실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md)의 "여러 해결안이 있고 게임 디자인에 영향을 주면 임의로 확정하지 않고 선택지와 영향을 보고한다"와 짝을 이룬다. 이 스킬은 **추천하기 전에, 애초에 무엇을 추천해야 할지조차 불확실한 경우**를 다룬다.

반대로 다음은 발동 대상이 아니다: 요청이 구체적이고 대상과 범위가 명확한 경우, [AGENTS.md](../../../AGENTS.md)나 [코딩 컨벤션](../../../docs/coding-convention.md) 같은 규칙 문서를 보면 답이 정해지는 경우. 이때는 바로 실행한다. 매번 확인 질문을 던지면 오히려 방해가 된다.

## 방법

1. **추측으로 채우지 않는다.** 불명확한 부분을 그럴듯한 기본값으로 임의 해석해서 진행하지 않는다. 미정인 값은 미정으로 두고, 필요하면 `{자리표시}`로 남긴다.
2. **무엇이 불명확한지 먼저 코드와 문서를 읽고 좁힌다.** 탐색 없이 바로 사용자에게 되묻지 않는다. 코드나 설정을 읽어 확인할 수 있는 것은 질문으로 되돌리지 않는다. 예/아니오로 답할 수 있는 질문은 최대한 스스로 조사해서 없앤 뒤, 정말 사용자만 결정할 수 있는 지점만 질문으로 남긴다.
3. **AskUserQuestion 툴로 구체적 선택지를 제시한다.** "어떻게 할까요?" 식의 열린 질문 대신, 조사한 내용을 바탕으로 2~4개의 실제 대안을 제시하고 근거를 덧붙인다. 추천 대안이 있으면 첫 번째 옵션에 "(권장)"을 붙인다. 기술적 트레이드오프가 있는 대안(아키텍처, 패키지, 동기화 방식 등)이면 [present-alternatives](../present-alternatives/SKILL.md)의 장단점 분석 틀을 먼저 적용한 뒤 그 결과를 선택지로 정리한다.
4. **질문은 실행에 필요한 만큼만.** 한 번에 필요 이상으로 여러 질문을 쏟아내지 않는다. 결정이 서로 독립적이면 한 번에 묶어 물어도 되지만, 뒤 질문이 앞 질문의 답에 따라 달라지면 순서대로 나눈다.
5. **답을 받으면 그 결정을 반영해 계획과 코드를 진행한다.** 같은 사안을 다시 묻지 않는다.

## 예시

```
사용자: "플레이어 이동 만들어줘"

❌ 바로 Rigidbody 기반 이동 스크립트와 NetworkTransform 동기화까지 임의로 작성
✅ 먼저 확인 -> C# 스크립트가 아직 없음, Input System 액션 에셋은 있음,
   Mirror는 설치됨, 기획서 없음
   -> 규칙 문서로 정해지는 것(폴더, 네임스페이스, 명명)은 묻지 않고 바로 따름
   -> AskUserQuestion으로 "이번 작업에 네트워크 동기화까지 포함할지",
      "CharacterController 기반인지 Rigidbody 기반인지"처럼
      실제로 결과물이 갈리는 지점만 질문
```

# 코드 소유권 확인

## 언제 발동하나

작업 대상 파일이 요청자 본인의 파트를 벗어나 다른 담당자 영역과 접촉할 때 발동한다. 판단 기준은 [에이전트 실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md)의 "shinshi 프로젝트의 승인 경계" 절과 [서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md) 2~3장이다. `.github/CODEOWNERS`에 경로별 담당이 지정되어 있으며, 파일에 없는 경로는 팀 합의 파트 구분을 따른다. 이 스킬은 그 기준을 실제로 적용하는 절차다.

**요청자가 {팀장}이면** 팀장 소유 영역(각 도메인의 `Net/`, `98.Servers/`, `01.Network/`, `00.Common/`, 통합)은 승인 질문(3번) 없이 바로 진행한다. 그 밖의 파트 영역에 대해 팀장에게 별도 권한이 있는지는 팀이 정하지 않았다(**미정**). 정해지기 전까지는 다른 팀원과 같은 절차를 따른다.

다른 팀원이 요청자일 때는 구체적으로 다음을 건드리기 직전 이 스킬 전체 절차를 따른다:

- 통합 씬 (이름 **미정**. 지금은 `Assets/Scenes/SampleScene.unity`뿐이다) — [씬 · 에셋 안전](../../../docs/unity/SCENE_AND_ASSET_SAFETY.md) 1장
- 요청자 본인 파트가 아닌 `Assets/01.Scripts/` 하위 도메인 폴더 (예: UI 담당이 적 도메인 폴더를 고침)
- {팀장} 소유 네트워크 코드: 각 도메인의 `Net/{이름}State.cs`(상태 클래스)와 처리기 인터페이스, `Assets/01.Scripts/98.Servers/`(AI·웨이브 하위는 해당 파트와 공동), `01.Network/`, `00.Common/`의 공용 요청·조회 계약. 새 네트워크 멤버(`[SyncVar]` · `[Command]` · Rpc)가 필요하면 직접 추가하지 않고 {팀장}에게 요청한다
- 상태 클래스의 읽기 프로퍼티·이벤트처럼 서버·표현이 함께 쓰는 멤버 이름을 바꾸는 변경, asmdef 참조 변경 ({팀장} 리뷰)
- `.gitignore`, `.gitattributes`, `.editorconfig`, `.github/`, `ProjectSettings/`, `Packages/` 등 저장소 공용 설정
- 네트워크 권위 경계를 바꾸는 변경 (서버 판정 ↔ 클라 로컬 처리 전환) — [네트워크 권위](../../../docs/unity/NETWORK_AUTHORITY.md)
- 외부 · 구매 에셋 원본 (`Assets/Mirror/`, `Assets/99.ThirdParty/` 포함)
- 파일 삭제, 대량 이동, 이름 일괄 변경
- 다른 사람의 담당 개발 씬 (`Dev_{파트}.unity` 등, 구성 미정)

승인 경계에서 "승인 없이 진행"에 해당하는 영역(자기 파트 `Assets/01.Scripts/` 도메인 폴더 — `Net/`·`98.Servers/`·`01.Network/` 제외, `Assets/09.Data/`의 자기 파트 SO 값, `docs/`, 자기 담당 개발 씬)은 이 스킬 대상이 아니다 — 바로 진행한다.

## 방법

1. **건드릴 파일 목록을 먼저 확정한다.** 편집을 시작하기 전에 이번 작업이 실제로 어떤 경로를 건드리는지 훑는다.
2. **소유자를 확인한다.** `.github/CODEOWNERS`의 경로 규칙을 먼저 본다. 규칙에 없는 경로는 팀 합의 파트 구분과 [서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md) 2~3장으로 해당 경로의 담당({팀장} / {파트} 담당 {팀원이름})이 지금 요청한 사람과 다른지, 혹은 통합 담당 승인이 필요한 영역인지 확인한다.
3. **[에이전트 실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md)의 승인 경계에서 등급을 확인한다.**
   - **사전 승인 필요** 영역이면: 이미 담당자 승인을 받았는지 사용자에게 묻는다. 받았다고 확인되면 진행하고, 안 받았으면 먼저 확인부터 하고 오도록 안내한 뒤 **여기서 멈춘다.**
   - **절대 하지 않음** 영역(다른 사람의 담당 개발 씬 저장, `Library/`·`Temp/`·`obj/` 등 생성물 수정, 히스토리 재작성, 다른 작업자의 변경을 근거 없이 되돌리기)이면: 기본적으로 거절한다. 사용자가 명확한 사유와 함께 강행을 요청하면 그 사유를 다시 확인한 뒤에만 진행한다 — 그냥 지나가지 않는다.
4. **직접 그 담당자에게 연락할 수단이 없다.** 이 스킬은 Claude가 팀원에게 대신 연락하는 게 아니라, 사용자가 실제로 확인했는지 확인하는 절차다. AskUserQuestion으로 "이미 담당자 확인받음 / 지금 가서 확인하고 올게 / 그래도 진행해줘(사유 설명)" 형태로 묻는다.
5. **범위가 애매하면(예: 공용 유틸리티처럼 특정 파트에 안 걸리는 코드) 위 기준 문서에 명시적 규칙이 없는지 먼저 확인**하고, 그래도 애매하면 사용자에게 확인한다 — 임의로 안전한 쪽으로 넘겨짚지 않는다.
6. 확인을 통과했으면 이후 작업에서는 같은 파일 범위에 대해 다시 묻지 않는다.

## 예시

```
요청: "UI 담당인데, 적 AI 판정 로직도 같이 손보고 싶어" (Assets/01.Scripts/{NN}.{적 도메인}/ 수정 필요)

❌ 바로 적 도메인 폴더 코드를 고침
✅ 팀 합의 파트 구분 확인 → 적 도메인 폴더는 {파트} 담당({팀원이름}) 소유
   → 에이전트 실행 정책 승인 경계: 다른 파트의 Assets/01.Scripts/ 폴더 = "사전 승인 필요"
   → AskUserQuestion으로 "담당자 확인받으셨나요?" 확인 후 진행
```

```
요청: "적 체력을 동기화하려고 EnemyState에 [SyncVar]를 추가해줘" (파트 담당 요청)

❌ Net/EnemyState.cs에 직접 [SyncVar]를 추가하거나 표현 컴포넌트를 NetworkBehaviour로 바꿈
✅ 서버·클라이언트 협업 3장: 상태 클래스(Net/)와 새 동기화 필드는 {팀장} 소유
   → {팀장}에게 요청했는지 사용자에게 확인. 아직이면 요청 내용을 정리해 주고 멈춤
```

# 대안 제시

## 언제 발동하나

구현 방식이 하나로 정해지지 않고, 실질적인 트레이드오프가 있는 대안이 2개 이상 있을 때 발동한다.

- 사용자가 직접 "어떤 방법이 있어?", "장단점 비교해줘", "이거 어떻게 구현하는 게 나아?" 라고 물을 때
- 기능을 구현하다가 갈림길을 만났고, 각 갈림길이 서로 다른 성능, 복잡도, 유지보수 특성을 가질 때
- 아키텍처, 패키지 도입, 동기화 전략(서버 판정 vs 클라 표현 범위), 데이터 구조, 저장 방식 등 나중에 되돌리기 비용이 있는 결정을 앞두고 있을 때

**반대로 다음은 대상이 아니다:**
- 정답이 사실상 하나뿐이거나, [코딩 컨벤션](../../../docs/coding-convention.md) 같은 규칙 문서를 보면 답이 정해지는 경우. 바로 실행한다
- 순수하게 사용자 취향이나 선호로만 갈리는 선택. 대안 분석보다 [clarify-ambiguous-request](../clarify-ambiguous-request/SKILL.md)로 바로 질문하는 편이 낫다
- 대안이 3개 넘게 억지로 만들어질 만큼 사소한 결정. 과잉 분석하지 않는다

## 방법

1. **먼저 이 프로젝트의 실제 제약을 읽는다.** 트레이드오프는 교과서 일반론이 아니라 shinshi 조건에 비춰 평가한다.
   - [AGENTS.md](../../../AGENTS.md): 필수 규칙, 브랜치와 소유 영역
   - [에이전트 실행 정책](../../../docs/ai/01_AGENT_EXECUTION_POLICY.md): 사전 승인 대상, 스코프 확장은 팀 합의 사항
   - [네트워크 권위](../../../docs/unity/NETWORK_AUTHORITY.md): "사람마다 다르면 서버" 판단 기준, 파생 계산 원칙, Mirror 매핑과 함정, 데디케이티드 서버 운영 원칙
   - [코딩 컨벤션](../../../docs/coding-convention.md): 폴더와 네임스페이스, Find 계열 지양, FixedUpdate 지양, GC 최소화, 매직넘버 금지
   - `Packages/manifest.json`, `ProjectSettings/ProjectVersion.txt`: 실제 설치된 패키지와 에디터 버전
2. **확정된 사실과 미정을 구분한다.** 확정: Unity 6000.4.7f1, URP, Input System, Mirror 96.11.3, 서버 권위, 데디케이티드 서버, 서버 구성(마을·던전·백엔드)과 호스팅 단계(로컬 → AWS, [네트워크 권위](../../../docs/unity/NETWORK_AUTHORITY.md) 7장). 미정: 서버 빌드 설정·인증 방식, 최대 인원(`{최대 인원}`), 게임 장르와 시스템(기획서 없음), 파트 구성(`{파트}`). 미정인 값을 사실처럼 전제하지 않는다.
3. **진짜 후보만 추린다.** 실무에서 고려할 가치가 없는 대안은 나열하지 않는다. 보통 2~4개면 충분하다. 선택지가 많다고 더 도움이 되지 않는다.
4. **대안마다 같은 틀로 설명한다:**
   - 한두 줄 요약 (무엇을 하는 방식인지)
   - 장점
   - 단점과 리스크
   - 이 프로젝트 조건에서의 영향:
     - 네트워크 권위 경계와 충돌하지 않는가 (판정은 `[Server]`, 표현은 클라)
     - 화면·입력·로컬 플레이어가 없는 데디케이티드 서버에서도 판정이 동작하는가
     - 코딩 컨벤션과 충돌하지 않는가
     - 새 패키지나 외부 에셋이 필요하면 Unity 6000.4, URP와 호환되는지 확인했는가, 설치는 사전 승인 대상임을 밝혔는가
     - 다인 접속 검증(M2 이상, 인원 조건이면 `{최대 인원}`)에 드는 비용
     - 스코프 확장이나 다른 파트 소유 영역을 건드리는가
5. **하나를 명시적으로 권장한다.** "정답은 없다"로 끝내지 않는다. 권장안과 그 이유를 이 프로젝트 조건에 근거해 분명히 말한다. 근거가 약하거나 결론이 미정 값(서버 빌드 설정, 최대 인원, 기획)에 달려 있으면 권장을 보류하거나 조건부로 권장하고, 무엇이 정해져야 판단할 수 있는지 설명한다. 없는 확신을 지어내지 않는다.
6. **최종 선택이 사용자의 몫으로 남는 경우**(취향, 팀 합의가 필요한 스코프 확장, 미정 값의 결정 등)에는 이 분석을 바탕으로 [clarify-ambiguous-request](../clarify-ambiguous-request/SKILL.md)의 AskUserQuestion 단계로 넘긴다. 분석글만 던지고 끝내지 않는다.
7. 사용자가 하나를 고르면 그 결정을 근거로 계속 진행하고, 같은 사안을 다시 묻지 않는다.

## 예시

```
사용자: "제한 구역이 줄어드는 걸 서버-클라 어떻게 동기화할까?"

❌ 서버 권위와 클라 계산 두 방식을 교과서적으로 설명만 하고 끝
✅ NETWORK_AUTHORITY.md의 판단 기준("사람마다 다르면 서버")과
   파생 계산 원칙(서버는 원본 값 하나, 표현은 클라)을 확인
   -> "서버가 반경 값만 동기화, 클라가 셰이더와 파티클로 표현"과
      "서버가 경계 표현까지 매 프레임 브로드캐스트"를 비교
   -> 전자를 권장: 후자는 대역폭 낭비이고 파생 계산 원칙과 맞지 않음.
      범위 밖 피해 판정은 어느 쪽이든 서버가 한다
```

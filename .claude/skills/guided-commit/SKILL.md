# 가이드 커밋

## 언제 발동하나

사용자가 지금 있는 변경 사항을 커밋하고 싶다는 의사를 밝히면 발동한다. 예: "커밋할게", "커밋해줘", "이거 커밋하자", "커밋 진행해줘".
**바로 `git commit`을 실행하지 않는다** — 아래 절차를 먼저 거친다.

이미 이 절차를 거쳐 사용자가 메시지까지 확정한 뒤 "그대로 커밋해"라고 재요청하는 경우는 재점검 없이 바로 실행한다.

## 절차

### 1. 변경 사항 파악

- `git status`, `git diff`(staged + unstaged 전부)로 무엇이 바뀌었는지 읽는다.
- `git branch --show-current`로 브랜치를 확인한다. 작업 브랜치는 담당자별 `feature/{팀원이름}`이다. `main` 위에 있으면 사용자에게 알리고 그대로 커밋할지 확인한다.
- 서로 관련 없는 변경이 섞여 있는지 확인한다 (예: 문서 수정 + 특정 시스템 코드 + 무관한 설정 변경).
- 새 에셋마다 `.meta`가 함께 있는지 본다. 빠졌으면 커밋 전에 알린다 ([씬 · 에셋 안전](../../../docs/unity/SCENE_AND_ASSET_SAFETY.md) 2장).

### 2. 커밋 기준 확인

- [커밋 컨벤션](../../../docs/commit-convention.md)을 매번 읽고 그 기준을 따른다. `<타입>: <무엇>` 제목(타입은 `feat`/`fix`/`refactor`/`docs`/`chore`), 한국어 제목, 필요할 때만 "왜"를 적는 본문, 커밋 하나에 한 가지 일.
- 브랜치 · PR 같은 공통 규칙은 저장소 루트 [`AGENTS.md`](../../../AGENTS.md)를 따른다.
- 컨벤션 문서에 없는 타입이나 형식을 임의로 만들지 않는다. 문서가 바뀌었으면 바뀐 쪽을 따른다. 사용자가 형식을 지정하면 그대로 쓴다.

### 3. 코딩 컨벤션 위반 점검 (C#/Unity 변경분만)

- 변경된 `.cs` 파일이 있으면 [코딩 컨벤션](../../../docs/coding-convention.md) 기준으로 diff를 검토한다. 자주 걸리는 것: 폴더 · 네임스페이스(0장, 1장), 네이밍(2장: `_camelCase` / `UPPER_SNAKE_CASE` / `PascalCase`), 매직넘버 금지(3장), 중괄호(4장: Allman, 단일 문장도 필수), 필드 정렬(7장), using 그룹 순서(8장), 네트워크 표면 · 서버 로직 분리(9장), 주석(12장), null 체크 관용구(13장), SerializeField vs public(14장), 가드 절(21장), Find 계열 API(22장).
- 위반이 있으면 **커밋 메시지에 지적만 하고 넘어가지 않는다 — 먼저 코드를 고친다.** 고친 뒤 무엇을 왜 고쳤는지 사용자에게 짧게 알린다.
- 고치려는 파일이 요청자 파트 밖이면(`Net/`, `98.Servers/`, `01.Network/`, `00.Common/` 등) 먼저 `check-code-ownership` 절차를 따른다.
- 코드가 아닌 변경(문서, 에셋, 씬, 설정)은 이 점검 대상이 아니다.
- 컨벤션 위반인지 스타일 취향 차이인지 애매하면 임의로 판단하지 않고 사용자에게 확인한다.

### 4. 커밋 단위로 묶기

- "커밋 하나에 한 가지 일"([커밋 컨벤션](../../../docs/commit-convention.md) 4장) 원칙에 따라 관심사별로 변경을 나눈다.
- 나뉜다면 몇 개의 커밋이 될지, 각 커밋에 어떤 파일이 들어가는지 목록으로 사용자에게 보여준다.
- 자연스럽게 하나의 작업이면 억지로 쪼개지 않는다 — 나누는 것 자체가 목적이 아니라 이력을 읽기 좋게 만드는 것이 목적이다.

### 5. 커밋 메시지·설명 작성

- 각 커밋 단위마다 `<타입>: <무엇>` 제목과, 필요하면 왜 했는지 본문을 작성한다. 타입이 헷갈리면 커밋 컨벤션 2장의 표를 본다.
- **`Co-Authored-By` 트레일러를 넣지 않는다** (커밋 컨벤션 5장). 도구 기본 설정이 붙이게 되어 있어도 제외한다. 이미 붙은 채로 커밋했고 push 전이면 `git commit --amend`로 지운다.
- 실제로 `git commit`을 실행하기 전에 사용자에게 메시지 전체(제목 + 본문, 여러 개면 각각 구분해서)를 보여주고 **확인을 받는다.**

### 6. 기준 문서를 코드와 동기화한다

커밋하는 변경이 **기능의 구현 상태나 팀 계약을 바꿨으면 그것을 서술한 문서도 같은 커밋에서 고친다.**
코드만 고치고 문서를 두면 다음 사람이 문서를 믿고 이미 있는 것을 다시 만들거나, 없는 것을 있다고 여긴다.

대상 문서와 판단 기준.

| 무엇이 바뀌었나 | 어느 문서를 |
|---|---|
| 최상위 폴더 · 도메인 폴더 · 네임스페이스가 새로 생겼다 | [코딩 컨벤션](../../../docs/coding-convention.md) 0장, 1장 (표에 없는 최상위 폴더는 먼저 표를 고친다) |
| 네트워크 멤버 · 서버/클라이언트 담당 경계가 바뀌었다 | [서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md), [네트워크 권위](../../../docs/unity/NETWORK_AUTHORITY.md) |
| 씬이 새로 생겼거나 씬 소유가 정해졌다 | [씬 · 에셋 안전](../../../docs/unity/SCENE_AND_ASSET_SAFETY.md) 1장 표 |
| 밸런스 데이터 구조 · 작업 방식이 바뀌었다 | [밸런스 데이터 작업](../../../docs/unity/BALANCE_DATA_WORKFLOW.md) |
| 기능 진입점이 새로 생겼다 | [프로젝트 지식 맵](../../../docs/ai/07_PROJECT_KNOWLEDGE_MAP.md) 표 |
| 빌드 · 테스트 명령이 생겼다 | 저장소 루트 `README.md` |
| 게임 규칙 · 스코프 · 기술 선택이 바뀌었다 | **(작성 예정)** 기획서 / 기술 설계 문서. 아직 없으면 사용자에게 알리고 새 문서를 임의로 만들지 않는다 |

지켜야 할 것.

- **현재와 계획의 구분을 실제 코드 기준으로 맞춘다.** 예를 들어 적 스폰이 구현되면 그 항목을
  계획에서 현재로 옮기고, 아직 연결되지 않은 하위 항목은 계획으로 남긴다.
  전부 되지 않았는데 통째로 현재로 올리지 않는다.
- **진행 중이면 진행 중이라고 적는다.** 완료 표시는 실제로 동작을 관찰한 것에만 한다.
  코드는 있지만 실행 검증을 하지 않았으면 `구현됨·실행 미검증`으로 적는다 ([문서 분류 기준](../../../docs/DOCUMENTATION_POLICY.md)).
- 문서와 코드가 다르면 **코드가 기준이다.** 문서를 코드에 맞추고, 차이를 사용자에게 보고한다.
- 기획 선택이 걸린 불일치(어느 쪽이 맞는지 팀이 정해야 하는 것)는 임의로 고치지 않는다.
  무엇이 충돌하는지만 사용자에게 알리고 그대로 둔다.
- 문서 수정은 코드와 같은 커밋에 넣는다. 따로 떼면 어느 커밋 기준의 문서인지 알 수 없게 된다.
  단, 문서만 대량으로 손보는 작업이면 문서 전용 커밋으로 분리한다.
- `.claude/` 아래 파일(스킬 등)은 여기서 말하는 기준 문서가 아니다.

### 7. 다른 담당자에게 넘길 것이 있으면 전달 문서를 만든다

커밋한 변경 때문에 **다른 파트가 해야 할 일이 생겼거나**, 작업 중에 다른 사람 소유 영역의 문제를
발견해 직접 고치지 못하고 남긴 것이 있으면, 그 담당자에게 건넬 문서를 따로 쓴다.

- 전달 문서는 `.claude/handover/{날짜}/{내용}.md`에 쓴다(`AGENTS.md` 기준, Git 제외, 커밋하지 않음). `{날짜}`는 작성일(`YYYY-MM-DD`)이다. 팀 전체가 지켜야 할 계약이 바뀌었으면 그 내용은 전달 문서와 별개로 `docs/`에 반영한다.
- 문서 이름은 누구에게 무엇을 넘기는지 알 수 있게 짓는다. 예: `{파트}-전달-적스폰-정리.md`
- **이 문서는 그대로 복사해서 상대에게 건넨다. 따라서 자립적이어야 한다.**
  다른 문서 경로나 저장소 내부 문서를 참조하지 않는다. 내부 약칭도 풀어 쓴다.
  받는 사람이 이 파일 하나만 보고 착수할 수 있어야 한다.
- 담을 것: 왜 지금 보내는지, 증상, **재현 절차**, 원인(파일과 메서드까지), 제안, 예상 비용, 권하는 순서,
  되물을 창구. 상대 파트 코드를 대신 고치지 않고 판단은 상대에게 맡긴다.
- 네트워크 멤버(`[SyncVar]` · `[Command]` · Rpc)나 `98.Servers/`의 {팀장} 소유 코드 변경이 필요하면 직접 추가하지 않고 {팀장}에게 요청하는 전달 문서를 쓴다 ([서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md) 3장).
- 세션 인수인계(`write-handoff` 스킬, [세션 인수인계](../../../docs/ai/05_SESSION_HANDOFF.md))와 혼동하지 않는다. 인수인계는 **다음 세션의 나**를 위한 것이고,
  전달 문서는 **다른 사람**에게 건네는 것이다. 둘 다 필요하면 둘 다 쓰고, 인수인계 쪽에서 전달 문서 경로를 가리킨다.

### 8. 확인 후 커밋

- 승인받은 내용 그대로 커밋한다. 사용자가 메시지 수정을 요청하면 반영 후 다시 확인받는다.
- push는 이 스킬의 범위가 아니다 — 별도로 명시적인 요청이 있을 때만 한다.

## 하지 않는 것

- 사용자 확인 없이 바로 `git commit` 실행
- 코딩 컨벤션 위반을 발견하고도 그냥 커밋
- 서로 관련 없는 변경을 하나의 커밋에 몰아넣기
- 커밋 컨벤션에 없는 타입 · 형식을 새로 만들어 쓰기
- 커밋 메시지에 `Co-Authored-By` 트레일러 넣기
- `.meta` 없이 에셋만 커밋하기
- 요청받지 않은 push
- 전달 문서에 저장소 내부 문서 경로를 참조로 남기기 - 복사해서 건네는 순간 끊긴다
- 다른 파트가 해야 할 일을 커밋 메시지에만 적고 전달 문서를 만들지 않기
- 구현 상태가 바뀌었는데 기준 문서를 그대로 두고 커밋하기
- 검증하지 않은 기능을 문서에 현재나 완료로 표시하기

## 공유 문서와 개인 기록의 경계

[문서 분류 기준](../../../docs/DOCUMENTATION_POLICY.md)을 따른다.

- 팀원에게 필요한 계약·사용법·담당자 인계는 `docs/`에 자립적으로 작성한다.
- 개인 실행 이력·계정/비용·모델 선호·다음 세션 기록은 Git에서 제외되는 개인 기록 영역에 보관한다(세션 기록은 `.claude/docs/`, 전달 문서는 `.claude/handover/`. 기준은 `AGENTS.md`).
- `docs/` 문서가 개인 기록을 읽어야만 이해되는 구조를 만들지 않는다. 필요한 공용 사실은 공유 문서 본문에 적고 코드·공유 문서를 근거로 삼는다.

# 가이드 이슈 등록

## 언제 발동하나

사용자가 지금 이야기한 문제나 작업을 GitHub 이슈로 남기고 싶다는 의사를 밝히면 발동한다.
예: "이슈 올려줘", "이슈로 등록해줘", "버그 이슈 만들어줘", "이거 이슈로 남겨두자".

**바로 `gh issue create`를 실행하지 않는다** — 아래 절차를 먼저 거친다.
이미 이 절차로 본문을 확정한 뒤 "그대로 올려"라고 재요청하는 경우는 재점검 없이 실행한다.

## 절차

### 1. 템플릿을 고르고 매번 읽는다

`.github/ISSUE_TEMPLATE/` 폴더를 열어 무엇이 있는지 확인하고, 등록할 내용에 맞는 것을 고른다. 지금은 `01-task.yml`(작업), `02-bug.yml`(버그), `03-balance.yml`(밸런스) YAML 폼이 있다.

- **제목 접두어와 라벨은 템플릿 파일에 적힌 값을 그대로 쓴다.** 기억으로 재구성하지 않는다.
  템플릿이 바뀌었으면 바뀐 쪽을 따른다.
- 템플릿이 YAML 폼이면 `gh issue create`로는 폼을 채울 수 없다.
  **각 필드의 `label`을 그대로 Markdown 제목(`### 라벨명`)으로 옮겨 본문을 만든다.** 섹션을 빼거나 순서를 바꾸지 않는다.
- `dropdown`은 고른 값 한 줄로, `checkboxes`는 `- [ ]` / `- [x]` 목록으로 적는다.

템플릿 폴더가 없어졌거나 읽을 수 없을 때만 아래 대체 형식을 쓴다. 제목 접두어는 구분용 **제안**이다. 사용자가 다른 형식을 원하면 따른다.

| 무엇을 남기나 | 제목 접두어 | 본문 섹션 |
|---|---|---|
| 아직 안 만든 개발 작업 | `[작업] ` | 목표 / 완료 조건 / 관련 파트 / 관련 이슈·PR |
| 동작하지 않는 것 | `[버그] ` | 증상 / 재현 순서 / 기대 동작 / 실제 동작 / 네트워크 관련 / 심각도 / 콘솔 로그 / 확인한 것과 못 한 것 |
| 수치 조정 제안 | `[밸런스] ` | 대상 데이터 / 현재 값 / 제안 값 / 이유 / 확인 방법 |

- 어느 형식에도 맞지 않으면 사용자에게 어느 쪽으로 낼지 묻는다. 임의로 새 형식을 만들지 않는다.
- 밸런스 수치를 다루면 [밸런스 데이터 작업](../../../docs/unity/BALANCE_DATA_WORKFLOW.md)의 용어와 데이터 위치를 따른다.

### 2. 같은 이슈가 이미 있는지 본다

```bash
gh issue list --state all --search "핵심 키워드"
```

- 같은 증상이 이미 있으면 **새로 만들지 않고** 그 번호를 사용자에게 보여주고 댓글로 덧붙일지 묻는다.
- 닫힌 이슈에 같은 증상이 있으면 재발인지 확인한다. 재발이면 새 이슈에 그 번호를 참조로 적는다.

### 3. 사실만 모은다 — 추측으로 채우지 않는다

이슈는 다른 사람이 그것만 읽고 착수하는 문서다. 틀린 단정 하나가 남의 반나절을 쓴다.

- **재현 순서는 실제로 관찰한 순서로 적는다.** 몇 명으로, 어느 씬에서, 무엇을 했을 때인지.
  사용자가 말한 것을 그대로 쓰고, 빠진 단계는 지어내지 않고 사용자에게 묻는다.
- **모르는 항목은 비운다.** 특히 버그의 `네트워크 관련`(서버만/클라만/양쪽/단일 플레이)은
  확인되지 않았으면 체크하지 않고, 그 아래에 "아직 확인되지 않았다, 다음 재현 때 먼저 채운다"를 적는다.
  다인 접속에서 본 버그면 테스트 등급(M0~M3)도 적는다 ([멀티플레이 테스트](../../../docs/ai/04_MULTIPLAYER_TEST_PROTOCOL.md) 1장).
- **심각도는 증상으로 정한다.** 크래시·진행 불가면 `치명`, 핵심 기능이 틀리게 동작하면 `높음`,
  우회 가능하면 `보통`, 보이기만 이상하면 `낮음`.
- 원인을 아직 모르면 "원인 미확인"이라고 쓴다. 의심 지점이 있으면 **의심이라고 표시하고** 파일·메서드까지 적는다.
- 이미 확인한 것과 확인하지 못한 것을 나눠 적는다. 받는 사람이 어디서부터 이어받을지 알 수 있어야 한다.

### 4. 버그면 로그를 실제로 찾아본다

"로그 없음"이라고 쓰기 전에 아래를 직접 확인하고, **찾아본 곳과 결과를 본문에 남긴다.**
경로의 `DefaultCompany\shinshi`는 `ProjectSettings/ProjectSettings.asset`의 `companyName`·`productName` 값이다. 바뀌었으면 그 값으로 찾는다.

| 어디 | 무엇 |
|---|---|
| `%USERPROFILE%\AppData\LocalLow\DefaultCompany\shinshi\Player.log` | 빌드 실행 로그. 직전 실행은 `Player-prev.log` |
| `%USERPROFILE%\AppData\Local\Temp\DefaultCompany\shinshi\Crashes\` | 크래시 덤프(`crash.dmp` + `error.log`) |
| `%LOCALAPPDATA%\Unity\Editor\Editor.log` | 에디터에서 재현했다면 |

- 로그가 있으면 **꼬리에서 관련 구간만** 잘라 `콘솔 로그` 섹션에 넣는다. 수백 줄을 통째로 붙이지 않는다.
- 없으면 없다고 쓰고, **다음 재현 때 어디서 무엇을 가져오면 되는지** 경로를 적어 둔다.
  다인 접속 테스트는 인스턴스·PC마다 로그가 따로 남으므로 어느 쪽의 것인지도 함께 적는다.
- 크래시 난 쪽이 서버인지 클라이언트인지는 로그가 없으면 알 수 없다. 모르면 모른다고 쓴다.

### 5. 라벨 · 담당자 · 마일스톤

- **라벨은 템플릿에 적힌 것만 붙인다.** 없는 라벨을 새로 만들지 않는다.
  템플릿의 라벨이 저장소에 아직 없을 수 있으므로 `gh label list`로 확인한다. 저장소에 없으면 그 라벨 없이 만들고 사용자에게 알린다.
- **담당자는 원인이 어느 파트인지 확정됐을 때만 지정한다.**
  `.github/CODEOWNERS`에서 해당 경로의 소유자를 먼저 찾고, 규칙에 없으면 팀 합의 파트 구분과 [서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md) 2장(`Net/`, `98.Servers/`, `01.Network/`, `00.Common/`은 {팀장})으로 소유자를 찾아 사용자에게 확인하고 붙인다.
  원인 파트가 아직 불확실하면 **비워 둔다** — 엉뚱한 사람에게 배정하면 그 사람이 확인하는 시간만 쓴다.
- 마일스톤은 일정 판단이다. **임의로 고르지 않고 사용자에게 묻는다.** 저장소에 없는 마일스톤을 만들지 않는다.
- 관련 PR·커밋·다른 이슈가 있으면 본문 끝에 번호로 연결한다. **번호를 지어내지 않는다.**

### 6. 사용자 확인 후 생성

- `gh issue create`를 실행하기 전에 **제목과 본문 전체, 라벨과 담당자를 함께 보여주고 확인받는다.**
- 저장소는 `inha-2026-gamedevelop/shinshi`이다.
- 본문은 스크래치패드의 임시 파일로 넘긴다. 저장소 안에 임시 파일을 만들지 않고, 생성 후 남기지 않는다.

```bash
gh issue create --title "[버그] ..." \
  --body-file {스크래치패드 임시파일}
# 저장소에 맞는 라벨이 있으면 --label {라벨} 을 붙인다
```

- `gh`가 없거나 인증되지 않았으면 본문을 그대로 출력하고, 사용자가 웹에서 붙여넣을 수 있게 안내한다.
- 이슈 본문 끝의 생성 표기는 이 스킬이 따로 정하지 않는다. 세션 지침이 요구하면 따른다.
- 생성 후 이슈 URL을 보고한다.

### 7. 이슈를 만든 뒤에 할 것

- 진행 중인 PR의 `검증`에 남긴 미검증·남은 항목과 관련 있으면 **이슈 번호를 그쪽에도 적는다.**
  PR 본문과 이슈가 서로를 가리켜야 나중에 이력을 따라갈 수 있다.
- 다른 파트가 받아야 할 일이면 이슈만 남기지 말고 전달 문서(`guided-commit` 7절)도 함께 만들지 사용자에게 묻는다.
  이슈는 저장소에 남는 기록이고, 전달 문서는 상대에게 복사해 건네는 자립 문서다.
- 세션을 여기서 끊는다면 인수인계(`write-handoff`)에 이슈 번호를 남긴다.

## 하지 않는 것

- 사용자 확인 없이 `gh issue create` 실행
- 템플릿(또는 대체 형식) 섹션을 임의로 빼거나 순서를 바꾸기
- 확인하지 않은 항목을 채우거나 체크하기 — 특히 버그의 `네트워크 관련`과 심각도
- 로그를 찾아보지 않고 "로그 없음"이라고 쓰기
- 원인이 불확실한데 특정 파트 담당자를 배정하기
- 없는 라벨·마일스톤을 새로 만들기
- 이슈 번호·PR 번호를 추측해서 적기
- 이미 같은 이슈가 있는데 중복으로 만들기

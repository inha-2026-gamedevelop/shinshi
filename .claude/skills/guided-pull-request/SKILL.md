# 가이드 풀 리퀘스트

## 언제 발동하나

사용자가 지금 브랜치의 작업을 PR로 올리고 싶다는 의사를 밝히면 발동한다.
예: "PR 올려줘", "풀리퀘 보내자", "풀리퀘스트 만들어줘", "main에 PR 보내줘".

**바로 `gh pr create`를 실행하지 않는다** — 아래 절차를 먼저 거친다.
이미 이 절차로 본문을 확정한 뒤 "그대로 올려"라고 재요청하는 경우는 재점검 없이 실행한다.

## 절차

### 1. 브랜치와 커밋 상태 확인

- `git branch --show-current`로 현재 브랜치를 확인한다. `feature/{팀원이름}` 형식이어야 한다.
- **`main` 위에 있으면 PR을 만들지 않는다.** 사용자에게 알리고 멈춘다.
- `git status`로 커밋되지 않은 변경이 남았는지 본다. 남아 있으면 이번 PR에 포함할지 사용자에게 묻는다 — 임의로 커밋하지 않는다(커밋은 `guided-commit`의 범위다).
- `git fetch origin` 후 `git log origin/main..HEAD --oneline`으로 이번 PR에 들어갈 커밋 목록을 확인한다. 비어 있으면 올릴 것이 없다고 알리고 멈춘다.
- 푸시되지 않은 커밋이 있으면 `git push -u origin {브랜치}`가 필요함을 알리고 **사용자 승인을 받은 뒤** 푸시한다.

### 2. 변경 내용 분석

- `git diff origin/main...HEAD --stat`으로 변경 파일 전체를 본다.
- 커밋 메시지와 diff를 읽고 **무엇을 왜 했는지**를 스스로 요약할 수 있을 때까지 파악한다. 커밋 메시지를 그대로 나열하는 것은 요약이 아니다.
- 아래를 판정한다. 이후 본문 작성의 근거가 된다.
  - 씬 파일(`.unity`)이 포함됐는가. 통합 씬(이름 **미정**)이나 남의 담당 씬이 있는가 ([씬 · 에셋 안전](../../../docs/unity/SCENE_AND_ASSET_SAFETY.md) 1장).
  - `.meta` 없이 추가된 에셋이 있는가.
  - Mirror 관련 변경(`[Server]`, `[Command]`, `[SyncVar]`, `NetworkBehaviour` 등)이나 `Net/`, `98.Servers/`, `01.Network/`, `00.Common/` 변경이 있는가.
  - 대용량 바이너리(모델·텍스처·사운드)가 추가됐는가. LFS 대상 확장자면 `git lfs ls-files`로 LFS 포인터로 올라갔는지 확인한다. 대상이 아닌 대용량 파일이면 알리고, `.gitattributes`에 추가할지 사용자에게 묻는다 (같은 문서 3장). PR 검사 워크플로(`pr-guard.yml`)도 LFS 미적용 파일을 실패로 처리한다.
  - `.cs` 파일에 새 상수로 박힌 밸런스 수치가 있는가 ([코딩 컨벤션](../../../docs/coding-convention.md) 3장).

### 3. PR 크기 점검

넘으면 **막지는 말되 알린다.**

| 기준 | 권장 |
|---|---|
| 변경 파일 수 | 팀 기준 **미정**. `pr-guard.yml`은 시작값으로 15개 초과 시 경고한다. 한 PR은 한 가지 변경에 집중한다 |
| 씬 파일 | PR당 1개. 2개 이상이면 `pr-guard.yml`이 경고하고, 이유를 본문에 적는다 ([씬 · 에셋 안전](../../../docs/unity/SCENE_AND_ASSET_SAFETY.md) 1장) |

초과하면 "씬 M개 — 권장치 초과"처럼 알리고, 나눠서 올릴 수 있는 경계가 보이면 제안한다.

### 4. 본문 작성 — 템플릿 그대로

`.github/PULL_REQUEST_TEMPLATE.md`를 매번 읽고, 그 파일의 섹션 구조·순서·문구를 그대로 따른다.
템플릿이 바뀌었으면 바뀐 쪽을 따른다. 기억으로 재구성하거나 섹션을 임의로 추가·삭제하지 않는다. 안내용 HTML 주석(`<!-- ... -->`)은 지운다.

템플릿 파일이 없어졌거나 읽을 수 없을 때만 [`AGENTS.md`](../../../AGENTS.md)의 PR 항목을 섹션으로 삼는다. AGENTS.md가 바뀌었으면 바뀐 쪽을 따른다.

```markdown
## 변경 설명
## 관련 이슈
## 검증
## 스크린샷 / 영상
```

- **제목**: 브랜치가 `feature/{팀원이름}`이라 제목이 유일한 단서다. 무슨 기능인지 반드시 제목에 적는다. 형식은 [커밋 컨벤션](../../../docs/commit-convention.md) 6장대로 커밋 제목과 같은 `<타입>: <무엇>`을 쓰고, 여러 커밋이면 대표 타입 하나를 고른다.
- **변경 설명**: 무엇을 했는지 한두 문장. 제목에 "왜"가 안 드러나면 여기에 적는다. 담당 파트를 알면 함께 적는다. 파트 구분은 팀 합의를 따른다(`.github/CODEOWNERS`의 경로 규칙을 먼저 본다).
- **관련 이슈**: 아는 이슈 번호가 있으면 `Closes #N`. 모르면 사용자에게 묻는다. 번호를 지어내지 않는다.
- **검증**: 실행한 검증과 결과를 적는다. 리뷰어가 그대로 따라 할 수 있는 순서로 쓴다. **실행하지 못한 검증은 못 했다고 적는다**(AGENTS.md). 이번에 하지 않은 것, `미검증` 항목도 여기에 남긴다 ([검증 플레이북](../../../docs/ai/03_VERIFICATION_PLAYBOOK.md)).
- **스크린샷 / 영상**: 화면에 보이는 변경이 있으면 사용자에게 첨부를 요청한다. 없으면 섹션을 지운다.

### 5. 검증 항목은 근거가 있을 때만 체크

**확인하지 않은 항목을 체크하거나 완료로 적지 않는다.** 리뷰어는 이 내용을 신뢰하고 병합한다.

- 코드·파일로 확인 가능한 항목(씬 수정 여부, `.meta` 동반, 코드 상수 밸런스 수치, 대용량 바이너리)은 **직접 확인하고** 적는다.
- 실행해야만 아는 항목(Console 경고·에러, Test Runner 결과, 다인 접속 테스트)은 **사용자에게 물어서** 답을 받은 뒤 적는다.
- 템플릿에서 해당 없는 섹션(예: 네트워크 변경이 없는 PR의 Mirror 섹션)은 통째로 지우지 말고 남긴 채 체크하지 않는다. 대신 사용자에게 "이 PR은 네트워크 무관으로 판단했다"고 알린다.
- **네트워크가 걸린 변경이면 다인 접속 테스트가 필수다(최소 M2).** 안 했으면 완료로 적지 않고, `미검증`으로 명시한다. 테스트 등급(M0~M3)은 사용자에게 확인해 채운다 ([멀티플레이 테스트](../../../docs/ai/04_MULTIPLAYER_TEST_PROTOCOL.md) 1장).

### 6. 리뷰어와 담당자 지정

**리뷰어를 반드시 지정한다. 생략하면 리뷰 없이 병합될 수 있다.**

`.github/CODEOWNERS` 규칙이 켜져 있어 변경 경로의 소유자에게 리뷰 요청이 자동으로 붙을 수 있다(작성자 본인은 제외). 붙는다고 가정하지 말고 PR을 만든 뒤 실제 리뷰어를 확인한다.

- **리뷰어는 {팀장}의 GitHub 계정을 기본으로 지정한다.** 계정이 아직 정해지지 않았거나 모르면 사용자에게 묻는다. 지어내지 않는다.
- `Net/`, `98.Servers/`, `01.Network/`, `00.Common/` 변경이 들어 있으면 {팀장} 리뷰가 필요하다 ([서버·클라이언트 협업](../../../docs/unity/SERVER_CLIENT_WORKFLOW.md)).
- **PR 작성자가 {팀장} 본인이면** 자기 자신을 리뷰어로 넣지 않는다. 다른 팀원이 요구사항·검증 증거를 리뷰하므로(같은 문서) 누구를 넣을지 사용자에게 묻는다. 임의로 고르지 않는다.
- 작성자 확인은 `gh api user --jq .login`으로 한다.
- **담당자(assignee)는 항상 `@me`로 넣는다.** 리뷰어와 담당자는 다르다 — 담당자는 이 작업을 책임지는 사람, 리뷰어는 봐줄 사람이다.

### 7. 사용자 확인 후 생성

- `gh pr create`를 실행하기 전에 **제목과 본문 전체, 그리고 지정할 리뷰어·담당자를 함께 보여주고 확인받는다.**
- 승인 후 실행한다. 저장소는 `inha-2026-gamedevelop/shinshi`, base는 `main`이다.

```bash
# 팀원이 올리는 PR — {팀장} 계정을 리뷰어로 지정한다
gh pr create --base main --head feature/{팀원이름} \
  --assignee @me --reviewer {팀장 GitHub 계정} \
  --title "..." --body-file {임시파일}

# {팀장}이 올리는 PR — 사용자가 고른 다른 팀원을 리뷰어로 지정한다
gh pr create --base main --head feature/{팀원이름} \
  --assignee @me --reviewer {리뷰할 팀원 GitHub 계정} \
  --title "..." --body-file {임시파일}
```

- 리뷰어 지정에 실패해도(권한·오타 등) PR 자체는 만들어진다. 실패하면 조용히 넘기지 말고 알린 뒤 `gh pr edit {번호} --add-reviewer {계정}`으로 다시 시도한다.
- 본문은 스크래치패드의 임시 파일로 넘긴다. 저장소 안에 임시 파일을 만들지 않고, 생성 후 남기지 않는다.
- `gh`가 없거나 인증되지 않았으면 본문을 그대로 출력하고, 사용자가 웹에서 붙여넣을 수 있게 안내한다.
- PR 본문 끝의 생성 표기는 이 스킬이 따로 정하지 않는다. 세션 지침이 요구하면 따른다.
- 생성 후 PR URL을 보고한다.

## 하지 않는 것

- 사용자 확인 없이 `gh pr create` 실행
- **리뷰어 없이 PR 생성** — 자동으로 붙을 거라 가정하기
- {팀장}이 작성자인 PR에 {팀장} 본인을 리뷰어로 넣기
- 리뷰어 계정을 추측해서 넣기
- 확인하지 않은 검증 항목을 체크하거나 완료로 적기
- `main`에서 PR 생성
- 템플릿(또는 AGENTS.md의 PR 항목) 섹션을 임의로 바꾸거나 빼기
- 이슈 번호·테스트 결과를 추측해서 채우기
- 승인 없이 push
